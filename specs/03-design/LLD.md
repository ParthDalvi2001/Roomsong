## 3. ECS design

This section is the wiring contract of the integration task T-128: which components and systems exist, in what order they run, what happens from page load to the first sound, and in what order the wiring is built. Written 2026-10-12 against `develop` at `44dfe39`. Every class, function, event and constant named here was read from the code; what is not on `develop` is marked **to build**, with the task that owns it and a proposed signature. IWSDK facts were checked against the installed packages (`@iwsdk/core` 1.0.1, `elics`, `three` 0.181.0) and cite the file. Nothing here has run on a headset: every "emulator" below means IWER. The names other tasks may rely on are in API_SPEC §1.10; this section is the design behind them.

**The design in ten lines.**
1. Two files wire the app. `src/index.ts` is the boot: it mounts the landing page and then loads `src/app.ts` (to build), which holds everything that needs the SDK. Wherever a spec says "`src/index.ts` wires, saves or emits", the code is in `src/app.ts`.
2. `src/app.ts` makes one of each page-wide object: the world, the audio engine, the flash guard, the store with its debounced saver, and the garden state holder. Nothing else makes one.
3. Per-frame work lives in ECS systems. One helper registers them in ascending priority. A system gets its collaborators as `configData` at registration and never looks another system up.
4. `GardenSystem` is a plain class, not an ECS system, and the one owner of `GardenState`. It runs the reducers inside the bus events that reach it and emits `garden:changed` with the diff.
5. A session is the time between `xr:sessionStart` and `xr:sessionEnd` on the bus, not an `XRSession`: a system reads XR objects only where it needs them, so the garden window (§11) runs the same systems.
6. In each session the bed is placed, the room is read once, the signature is computed and the visit is applied, in that order. Only then do plants sound and the tide show, so the garden never plays in the wrong key.
7. No system saves. `src/app.ts` hands every `garden:changed` and `settings:changed` to the saver, and flushes it on hide and at session end.
8. `xr.offer` is `"none"`: the page's Enter click is the only way in, and the audio context is made inside it.
9. A throw in one system's `update` would stop the render loop for good, so the register helper is the circuit breaker of §8.
10. State reaches a renderer or the audio engine on a change, never per frame; the room is read once per placement; a save is debounced.

The bed's pose (settled in T-106) is the transform of the entity that carries `BedAnchor`, not a component field: elics 3.4.2 has no matrix field type, and IWSDK gives every entity an `object3D`. Checked against `node_modules/elics/lib/types.d.ts` and `node_modules/@iwsdk/core/dist/ecs/entity.d.ts` (@iwsdk/core 1.0.1).
Panel controls are direct pinch targets (T-151: "large pinch targets over ray UI"). `ui/Panel.ts` attaches one `Interactable { kind: 'panel' }` per control, so a control goes through the same picker, hover cue and commit on release as a plant. ### 3.2 Systems and plain classes (order matters)
`PerfSystem(−100) → [IWSDK's own systems, −5 to 1] → RoomSystem(10) → HandSystem(20) → GazeDwellSystem(25) → OnboardingSystem(35) → GardenAudioSystem(40) → SeedSystem(49) → BedRenderSystem(50) → HaloSystem(52) → VineRenderSystem(53, Could) → ParticleSystem(54) → TuningRippleSystem(55) → CaptionSystem(60) → HintSystem(61) → PanelSystem(62)`

Retired numbers: 30 (`GardenSystem` is a plain class, below), 51 (`TideRenderSystem` is part of `BedRenderSystem`) and 99 (`PerfHudSystem` is `PerfSystem`, which must run first to time the frame).

**One way to register (to build, T-128a, in `src/app.ts`).** `register(world, System, priority, configData?)` calls `world.registerSystem(System, { priority, configData })` and then wraps that instance's `update` in the circuit breaker of §8: a throw is caught and logged (`log.error`), the system is stopped with `stop()` and started again with `play()` 1 s later. This is not optional. `World.update` calls each system with no catch (`node_modules/elics/lib/world.js`), IWSDK's loop calls `world.update` and then `renderer.render` (`setupRenderLoop` in `node_modules/@iwsdk/core/dist/init/world-initializer.js`), and Three.js asks for the next frame only after that callback has returned (`node_modules/three/src/renderers/webgl/WebGLAnimation.js`). One throw in one `update` therefore ends the frames for the rest of the page's life. `CaptionSystem.update`, as built, has no catch of its own; the helper covers it and every system that comes later.
`register` returns the instance. It throws, at start-up, when its priority is lower than the previous call's, and for a `configData` key the system's schema lacks (elics would drop that key in silence). What the frame path needs beyond it:
- IWSDK's own systems freeze the session the same way, and `iwsdk.config.json` turns on three that Roomsong does not use (scene understanding, environment raycast, grab). After the last `register`, the helper wraps every other system of `world.getSystems()` the same way.
- `PerfSampler.frame` runs in `scene.onAfterRender`, inside `renderer.render`, where no system's wrap reaches: the `onAfterRender` callback has its own catch.
- A query's `qualify` and `disqualify` callbacks run synchronously inside the caller's `addComponent` or `removeComponent` (`node_modules/elics/lib/query-manager.js`), so a throw in `BedRenderSystem`'s callback would leave `RoomSystem`'s placed step half done: a query callback catches its own throw.
- A bus handler is already safe: the bus catches and logs (API_SPEC §2). A promise continuation is not, which is why none does any work (RoomSystem, below).
What the helper can rely on, read from elics: `registerSystem` writes each `configData` entry to `this.config.<key>.value` and only then calls `init()`; systems are kept sorted by ascending priority; a stopped system is skipped by `update`.
**How a system gets its collaborators.** By `configData`, declared in the system's schema as `{ type: Types.Object, default: null }` and read once in `init()` (`this.config.engine.value as AudioEngine`). The keys are fixed in API_SPEC §1.10: `engine`, `guard`, `garden`, `room`, `bed`. Who takes which: `PerfSystem` `guard` and `engine`; `GardenAudioSystem` `engine`; `BedRenderSystem` `guard`, `engine` and `bed`; `SeedSystem` (T-127) `guard`; `PanelSystem` (T-151) `garden` and `room`; `RoomSystem`, `HandSystem` and `CaptionSystem` none. No system calls `world.getSystem`, and no module keeps a singleton of its own. One line of reason: it is the SDK's own way to hand a value to a system, it is visible at the one place where systems are registered, and it needs no new layer.
**Bus order.** Systems subscribe in `init()` and are registered in ascending priority, and the bus calls handlers in subscription order (API_SPEC §2). So the handlers of one event run in priority order too, after `GardenSystem`'s, which subscribes first. RoomSystem moves the bed before GardenAudioSystem and BedRenderSystem read its pose in the same `garden:changed`.

**`GardenSystem` (to build, T-128b): the state holder.** A plain class, like `PersistenceSystem`: it has no per-frame work, so it is not an ECS system, and `garden/` still loads no SDK code. It imports core's `bus`, `clock`, `flags`, `log` and `settings` (a new garden takes the live settings), and garden's own pure functions. Signature: API_SPEC §1.10. It subscribes in its constructor, before any system exists.
- `load(state)` is called once per page by `src/app.ts`, with the saved garden or `newGarden(clock.now(), settings.get())`. It emits `garden:changed` with every plant id in `diff.added`, so every consumer learns the state from the event and needs no getter. With `flags.autoplant` N > 0 and no plant in the state, it first plants N seeds of its own, so a reload does not add N more (API_SPEC §3; the wiring's test hook, read by nothing until now). Seed n of N (from 0) has the id `auto-<n>`, the five Must voices in turn (`DAILY_VOICES`), the hue n / N, and goes through `plantSeed` onto cell number `((flags.seed ?? 0) + 7n) mod 80` (ring = the number divided by 16, step = the rest; 7 shares no factor with 80, so no cell comes twice). The plants are the reducers' own and the same on every run.
- One private `commit(next, added, removed, changed)`: a reducer that changes nothing returns the same reference (API_SPEC §1.1), and then nothing is emitted. Otherwise the state is replaced and `garden:changed { state, diff }` is emitted. The diff is known from the reducer that ran; nothing compares two states.

`newGarden()` (FR-PER-03; the settings panel calls it, T-151): the state becomes `newGarden(clock.now(), settings.get())` with the old anchor pair carried over by `setAnchor`, because the bed has not moved; every kept undo token is dropped; a seed that is out goes back (`reason: 'reset'`); `garden:changed` has every old plant id in `removed`; then the visit runs with the session's signature, which issues the three starter seeds (`visits` is 0). Called before the session has its signature, or outside a session, it stops after the `garden:changed`: the new garden has `visits` 0, so it gets its starter seeds from the ordinary visit at the next `room:features`. Not handled here: `press` on the Listen orb, `gesture:palmsOut` and `gesture:wake` (T-148 adds the Listen state and `listen:*`), and `press` on a panel control (ui acts on it).
New, with the holder: the constant `UNDO_LIFE_MS = 5000` in `garden/config.ts` (FR-MUS-12), and two events in `garden/events.ts`, `garden:seedOut { seed: Seed; hand: Hand }` and `garden:seedBack { seedId: string; reason: 'offBed' | 'full' | 'lost' | 'reset' }`. The reason is there because the user is told different things: a bump for a release off the bed, "Garden is full" for a full bed (UX §7), nothing for the other two. `garden:seedArrived` keeps its payload and means what T-161 built it for: a seed joined the supply. **`RoomSystem` (to build, T-128c).** `init()` makes the bed's entity once, `this.world.createTransformEntity(undefined, { persistent: true })` (without `persistent` IWSDK parents an entity to the active level: `createTransformEntity` in `node_modules/@iwsdk/core/dist/ecs/world.js`), hidden, and the three adapters, the solver and `new RoomFeatureExtractor(planes, meshes)`. Three states:
- *idle*: no session. The bed is hidden and carries no `BedAnchor`.
- *placing*: from `xr:sessionStart`, or from `replace()`. The handler only hides the bed and takes `BedAnchor` off (on `replace()` it also calls `void anchors.clear()`). The first `update` after it, after the adapters' and the anchor store's `setFrame`, decides: from `xr:sessionStart` with a saved pair → `anchors.restore(handle, ANCHOR_RESTORE_TIMEOUT_MS)`, whose continuation only keeps the result (where anchors are not supported the store gives `null` at once, and then knows which anchor to delete later); otherwise `solver.run({ timeoutMs: PLANE_LEVELS_TIMEOUT_MS })`. A later `update` that finds a kept pose checks the reach (D-041: the level distance from the head to the bed centre is at most `BED_CENTRE_MAX_M` plus `RESTORE_REACH_SLACK_M`, 0.10 m and provisional, and the bed is in front of the user) and places the bed with `restored: true`; one that finds `null`, or a bed out of reach, calls `solver.run(…)`. A kept result is dropped on `xr:sessionStart` and `xr:sessionEnd`. The decision cannot be taken in the handler: `anchors.supported()` is false until the store has seen a frame, so a restore asked there would always fail and each session would leave one more anchor on the device (T-162 review). While the solver runs: each frame, after `setFrame`, `solver.update(head.elements, time × 1000)`. While the solver is at level 3 (`solver.preview()` is not null; to build, API_SPEC §1.3 first) the bed is shown at the preview's pose with a 100 ms ease and no `BedAnchor`, which is what makes it the ghost of UX §9.2, and one `Caption` is up, on an entity RoomSystem keeps for it: `placeLook`, or `placeLookGaze` when `settings.get().gazeDwell`, with `expiresAt = clock.now() + HIT_TEST_TIMEOUT_MS`. The confirm by hand: a `gesture:release` with `gesture: 'none'` and `target: null` calls `solver.confirm()`. Both conditions are needed: a cancelled press has `target: null` too, but its `gesture` is `press`, and it confirms nothing. `confirm()`, the gaze dwell's way in (T-160), calls the solver only while `solver.preview().level === 3`: a dwell never floats the bed (UX §9.2). A pause while placing: on `xr:visibility { visible: true }` in this state, `solver.run()` again; a restore in progress needs nothing, the store pauses its own time-out while the session is hidden. With a placed bed, after a recentre (the reference space's `reset`) or a pause: `anchors.restore(sameHandle, …)` again, which reads the anchor's pose with no device call, and the bed entity moves to it. The frame time runs on while the session is hidden, so the waits would otherwise be over in the first frame back.
- *placed*: the promise's continuation only keeps the placement (`this.placement = p`). The next `update`, after the adapters' `setFrame`, does the rest in this order: the entity's `position` and `quaternion` are set from `placement.pose`, raised by `state.bedHeightOffset`, and `updateMatrixWorld(true)` is called; the bed is shown; `BedAnchor` is added, with `heightOffset` and `source` passed to `addComponent` (`source` by level: `table`, `surface`, `hittest`, `floating`); the level-3 caption is taken back; `room:bedPlaced { placement, restored: false }`; then the room is read once, `features = extractor.extract(placement)`, and `room:features { features, surfaces: extractor.surfaces }` follows. Nothing else runs in the continuation: it runs after the frame's render, `this.xrFrame` is null there, and a throw there is caught by nothing. A room read there would come back empty with no error (`PlaneAdapter.read` swallows a frame read outside its callback), and every room would silently be Wanderer.
`xr:sessionEnd` → `solver.cancel()` and *idle*. The pending promise never settles (as built), so a late bed cannot arrive. A changed `state.bedHeightOffset` while placed moves the bed and calls `updateMatrixWorld(true)`. `placement.pose` is the surface's pose; where the bed is drawn is the entity's transform, offset included, and that is what every reader takes (above). The anchor steps of §5.5 slot in before `run()` and after `room:bedPlaced` with T-162; on that path the extractor cannot tell "no planes yet" from "no planes", so RoomSystem waits for planes, for at most `PLANE_LEVELS_TIMEOUT_MS`, before it extracts (API_SPEC §1.3).

**`HandSystem` (built by T-116; in review, so this may still change).** As T-116 handed it back (its API_SPEC §1.4, "HandSystem as built"): an ECS system for priority 20 with its own `HandSampler` (`readonly sampler`), attached on `xr:sessionStart` with `renderer.xr.getSession()` and detached on `xr:sessionEnd`; outside a session it does nothing. Each frame: `sampler.setFrame`, the context, then per hand `sample`, `machine.update` and the `HandState` write (one entity per hand; the component is in the manifest). Its time is `clock.now()`, core's wall clock, not the frame time. What that fixes for the wiring:
- An `Interactable`'s `kind`, `id` and `radius` are read once, when the component is added: whoever attaches one passes them to `addComponent` and never sets them afterwards. Only `worldPos` is read every frame.
- The bed is the entity that carries `BedAnchor`, the one added last, and `bedPose` is `null` while there is none. The ghost carries none, so no cell is hovered on it.
- Every cell counts as free until the first `garden:changed`: `GardenSystem.load` must have run before the first session, which sequence A7 gives.
- `hands:lost` is `{ hand, held }`, and the system raises the hand hint itself (`handOutOfView`), on that hand's own entity. Drawing the hover cue and the tint is T-119's.
- It has no way to swap its input source. The garden window (T-114) adds one to `hands/` when it needs it.

**`GardenAudioSystem` (to build, T-128d).** It keeps the latest `state.plants` from `garden:changed`, its own 16-number copy of the bed pose it last synced with, and a flag, *tuned*, for "this session has its signature". `room:signature` → `engine.setSignature(signature)`, *tuned* on, `engine.syncPlants(plants, bedPose)`, the pose read from the `BedAnchor` entity and copied. `garden:changed` and `room:bedPlaced`, while *tuned* → `syncPlants` again (it returns at once when nothing changed). `xr:sessionEnd` → *tuned* off and `syncPlants` with one shared empty list and the kept copy of the pose (`BedAnchor` is already gone when this handler runs), so the next session cannot start with the last session's plants at the last session's place. Before the signature nothing is synced: the engine's own default is C major pentatonic, and a restored garden must not be heard in it first. `update` → `engine.setListenerPose(head.elements)`.

**`BedRenderSystem` (to build, T-128c and T-128d).** `init()` makes `BedRenderer(bed)`, `PlantRenderer(bed, guard)` and `TideRenderer(bed, guard)` on the bed's `Object3D`, which it gets as `configData`. A query on `BedAnchor` tells it whether the bed is placed, and it starts as not placed: on `qualify` the cell markers show, `plants.setState(state)` runs and the plants' targets are made; on `disqualify` the markers hide (`BedRenderer.setGhost(true)`, to build), the plants are cleared and their targets destroyed. `garden:changed` while placed → `plants.setState(state)` with the whole state (the renderer picks what it needs: `plants` today, `lastVisitAt` too once T-119 draws the growth stage) and the targets of the ids in the diff are made, moved or destroyed. A plant's target is an entity from `this.createEntity()` with `Interactable { kind: 'plant', id, radius: HIT_RADIUS_M }`, all three passed to `addComponent` (hands reads them once, above), and its `worldPos` (through `getVectorView`) at the plant's cell centre on the bed, in world space. The bed moving under placed plants: `RoomSystem` moves it inside its own `garden:changed` handler, which runs first; this system's handler of the same event compares `state.bedHeightOffset` with the one it saw last and, when it differs, rewrites every target's `worldPos`. `update` → `phase = placed && tuned && engine.clock.now() > 0 ? engine.clock.barPhase() : NaN`, then `plants.update(phase, time × 1000)` and `tide.update(phase, time × 1000)`. The `NaN` matters twice: before `init()` the engine's `barPhase()` is 0, which the tide would draw as a wedge standing on step 0, and during Re-place the tide would otherwise sweep over the ghost. Each of the two query callbacks catches its own throw (above). **One request per plant:** `PlantRenderer.update` makes the one `guard.request` a plant gets per frame; a second light effect on a plant (the hover glow, the bloom, the Listen foreground) is handed to `PlantRenderer` and combined there, and no system asks the guard for a plant's element itself.

**`src/app.ts` (to build, T-128a, then every step).** Besides making the objects and registering the systems it does what needs both ends: it emits the three `xr:*` events, gives the landing page its `enter`, loads and saves, sets `renderer.xr.setFoveation(FOVEATION_MEDIUM)` once (Three.js applies it at each session start), and raises two captions, each on its own entity (a `Caption` added again to an entity that still has one does not qualify again, and the second would be lost), each with `expiresAt = clock.now() + 5000`: `E_SAVE_FAILED` from the saver's `onSaveFailed`, and `E_AUDIO_CONTEXT` when a session has no sound (sequence B says when). Sequences: §3.3.
**How a browser test reaches the objects.** The bus is reachable already (a test imports `/src/core/index.ts` from the dev server and gets the app's own instance), and most proofs of §3.5 are events. For the rest, when `flags.dev` is on, `src/app.ts` puts `{ world, engine, garden }` on `window.__roomsong`. Nothing in `src/` reads it, and without the dev gate it is not there.
**Why one render system for bed, plants and tide.** The three renderers share one parent (the bed's `Object3D`), one state event and one phase; three systems would each look the same things up. The halo, the particles and the ripple are their own systems because their tasks own them.

### 3.3 Sequences
Each step says what can fail and what the user then sees. "Device" marks what only a headset can show.

**A. Page load to a usable Enter button.**
1. `index.html`, `landing.css` and the boot chunk load. The boot chunk is `src/index.ts` and what it imports: `ui/Landing.ts`, `ui/strings.ts` and core without `core/components.ts`. It holds no SDK and no Three.js code. `mountLanding(root)` puts the whole page on screen: name, a disabled Enter with "Getting the garden ready.", the four device lines, the toggles, Help. The page asks `isSessionSupported('immersive-ar')` itself.
   *Fails:* no JavaScript → the `<noscript>` line. No immersive AR → the status says `E_XR_UNSUPPORTED` and Enter stays disabled (the garden window, T-114, takes over here).
2. `src/index.ts` calls `import('./app.js')`: the app chunk, with the SDK. *Fails* (network, a script error) → `landing.failed()`: "The garden could not load. Reload the page."
3. `src/app.ts` starts two things side by side: `World.create(container, projectOptions)` and `openStore()` followed by `store.load()`. *Fails:* `World.create` rejects (no WebGL, the scene file missing) → `landing.failed()`. The store cannot fail the start: `openStore()` never rejects and settles within `IDB_OPEN_TIMEOUT_MS` (1500), and `load()` gives `null` for nothing saved, unreadable storage or a corrupt save (moved to a backup, API_SPEC §4).
4. Saved settings go into the live store, under what the visitor has already changed on the page: `settings.set({ ...validateSettings(saved.settings), ...touched })`, where `touched` holds the keys whose live value differs from `DEFAULT_SETTINGS`. Without the second part, a box ticked while the save was loading would be unticked again.
5. One of each: `createAudioEngine()`, `new FlashGuard()`, `new GardenSystem()`, `new PersistenceSystem(store, onSaveFailed)`. `renderer.xr.setFoveation(FOVEATION_MEDIUM)`. The `XRInputVisualAdapter.createVisual` override of D-027 moves here from `src/index.ts`, because it imports the SDK.
6. The systems are registered with `register`, in ascending priority (§3.2).
7. `garden.load(saved ?? newGarden(clock.now(), settings.get()))`: the first `garden:changed`. Every system is subscribed by now.
8. Only now `src/app.ts` subscribes its two save handlers (sequence G), with `garden.state` as the last state seen, so the garden that was just loaded is not written straight back. If `settings.get()` differs from that state's `settings`, it calls `saver.save` once: a box ticked on the landing page is then saved even when no session follows.
9. `renderer.xr` gets its `sessionstart` and `sessionend` listeners, and `landing.ready(enter)` makes Enter usable.
Steps 3 to 9 run in one `try`: any throw → `log.error` and `landing.failed()`, so a fault in the wiring cannot leave the page saying "Getting the garden ready." for good.

Two numbers, both device-only. *Page load to a usable Enter:* at most 5 s on a Quest 3 over Wi-Fi, which is how this contract reads the cold start of Golden Rule 4; the page itself is readable after step 1, long before. *Enter click to the first XR frame:* at most 5 s (FR-SYS-06 as TC-DEV-01 measures it; the emulator's limit is 10 s, BUG-003). Nothing may be added between the click and the session request: the store is already open, the systems are registered, and the audio graph is built inside the click.

**B. The Enter click.** `Landing` calls `enter` synchronously inside the click (as built). `enter` does two things in that same call stack, and awaits neither before the other:
1. `engine.init()`. It makes the `AudioContext` and the graph and asks the context to run before its first `await` (as built), so all of that is inside the gesture. A rejection is logged as `E_AUDIO_CONTEXT` and remembered.
2. `world.launchXR()`, which calls `navigator.xr.requestSession` in the same stack (`launchXR` in `node_modules/@iwsdk/core/dist/init/xr.js`).
3. It returns the promise that resolves when `world.sessionRequestPending` has cleared, with `world.session !== undefined` (as built today).

*Fails:* the request is refused (no hand tracking, a permission declined) → the promise gives false, the page says `E_HANDS_UNAVAILABLE` and Enter stays usable; `enter` then calls `engine.suspend()`, so no context runs on a page without a session. No sound → the session still starts, the caption "Sound unavailable" (`E_AUDIO_CONTEXT`, a new key in `core/strings.ts`; the wording is UX's) shows once, and the garden works without sound and without the sweep of light, which runs on the audio clock. There are three ways to have no sound, and the caption covers all of them. (1) `engine.init()` rejected: raised at `xr:sessionStart`. (2) A session started and `init()` was never called: treated like (1). That is not possible through the page, but the dev plugin's `nativeXRControl` mode sets `launchOnSessionGranted: true` itself (`createProjectVirtualModuleSource` in `@iwsdk/vite-plugin-dev`), a second way in with no click, and it is the mode a headset day may use. (3) The browser never starts the context: `ctx.resume()` then stays pending and nothing rejects (`await g.ctx.resume()` in `AudioEngine.ts`), which is the likeliest failure on a device. So the caption is also raised `AUDIO_START_GRACE_MS` (3000, a constant of `src/app.ts`) after `xr:sessionStart` when `engine.clock.now()` is still 0; the timer is dropped at `xr:sessionEnd`. Device: whether the Quest Browser lets both calls share one click is not verified; audio first is the order that asks least of it.
**`xr.offer` is `"none"`.** With `"always"`, as `iwsdk.config.json` has it today, IWSDK also calls `navigator.xr.offerSession` once the world is ready (`manageOfferFlow` in `world-initializer.js`), and a session the browser starts from that offer never passes through the page's click: no audio context, and no way to test on a headset what would start one later. With `"none"` there is one way in, the same in the emulator and on the device. The price: the emulator's own "Enter XR" button and `iwsdk xr enter` both need an offered session (the CLI says so itself), so `enterXR` in `tests/e2e/support/iwer.ts` presses the page's button instead, as `enterFromLanding` in `08-landing.spec.ts` already does. `"none"` must be written out: IWSDK's default is `"always"`.

**C. Session start to the bed.**
1. Three.js fires `sessionstart`. `src/app.ts` takes the session from `renderer.xr.getSession()` (IWSDK sets `world.session` only after this event: `adoptXRSession` in `xr.js`), calls `landing.granted(session.enabledFeatures)`, listens for the session's `visibilitychange` (sequence F) and emits `xr:sessionStart { visible: true }`. The page hides; `HandSystem` attaches its sampler; `RoomSystem` goes to *placing*. The no-sound cases of B are checked from here.
2. With a saved anchor pair, the restore of §5.5 comes first, for at most 4 s (T-162). Without one, or when it fails, the chain:

| Level | Starts | Waits at most | The user sees | Ends with |
|---|---|---|---|---|
| 1, 2: a table, then any level surface in reach | at once, when the session has plane detection | `PLANE_LEVELS_TIMEOUT_MS` (3000), both together | the room, nothing else (the scanning ripple of UX §3.2 is not part of T-128) | a plane in reach → the bed on it |

**D. To the signature**, in the same `RoomSystem.update` as step 3.
4. `RoomSystem` reads the room once and emits `room:features`. `GardenSystem` emits `room:signature`. `GardenAudioSystem` tunes the engine and only then hands it the plants; `BedRenderSystem` lets the tide show. 5. `GardenSystem` applies the visit: `garden:changed`, then `garden:grown` and `garden:seedArrived` as they apply. A new garden has its three starter seeds now. *Fails:* no feature known → Wanderer (C major pentatonic, 0.9 s), not an error. A visit that is refused → no new seeds this session, logged.
   **The budget of this one frame.** It stacks the room read (`extract`), a change of key (`AudioEngine.setSignature`: about 0.15 ms for the call since T-143, which spread the rendering over the engine's own ticks; before that it was about 23 ms in Node), `syncPlants`, `setState` and the making of up to 80 targets. It is allowed 50 ms of script time, once per placement, while the bed is appearing; every other frame keeps the 6 ms of HLD §7. Step d2 of §3.5 measures it with a full bed. If it is over, the plants' part moves to the next frame: `GardenAudioSystem` and `BedRenderSystem` set a flag in the `room:signature` handler and do the sync and the draw in their next `update`. Not built until the measurement asks for it.

**E. To the first seed and the first sound.**
6. A palm held up for `PALM_UP_HOLD_MS` (400) → `gesture:palmUp` → `garden:seedOut` → the seed is at that hand's `palmPos` (T-127 draws it and gives it its `Interactable`).
7. The other hand pinches it (`gesture:pinchStart` with the seed as its target; from here the seed is drawn at that hand's pinch point, `HandState.pinchPos`, not on the palm), carries it and lets go over the bed → `gesture:release { gesture: 'carry', cell }` → `plantSeed` → `garden:changed` with the plant in `added` → `syncPlants`, `setState`, the plant's target. *Fails:* a release off the bed (`reason: 'offBed'`), or with the bed full (`'full'`) → `garden:seedBack`, and the seed is in the supply again. The hand lost for longer than the grace (T-116) → the same, with `'lost'`.
8. The first sound is that plant's note when the tide next reaches its step: at most one bar later, 2.86 s at 84 BPM. Nothing sounds at the release itself until T-147 (`preview`) and T-164 (`ui`) fill those calls in.

**The first-sound budget (FR-UI-02, 20 s), as constants.** Entry (5 s, device) + the plane wait (`PLANE_LEVELS_TIMEOUT_MS`, 3 s at most; 0 when a table is seen in the first frame) + the level-3 wait (0 with a table; else the time to the pinch, at most `HIT_TEST_TIMEOUT_MS`) + the tuning (4.0 s, and only if onboarding holds its first caption until `room:tuned`, T-150) + the seed (about 0.4 s of palm up, then the pinch and the carry) + up to one bar. With a table: 5 + 0..3 + 4 = 9 to 12 s before the first caption. With no table and no pinch: 5 + 3 + 10 + 4 = 22 s, over the limit before any seed (UX §9.2; the project owner chooses between a shorter level-3 wait, a shorter tuning for a bed-only room, and a rule scoped to rooms with a table). Each choice is one line: the first is `HIT_TEST_TIMEOUT_MS`, the second is the ripple's own timeline (T-142), the third changes no code. The wiring itself never holds a seed back: `GardenSystem` hands one out as soon as the visit is applied, so a player who opens a hand during the ripple gets it.

**F. Pause** (the headset comes off, or the session is otherwise hidden). The `XRSession` fires `visibilitychange`. `src/app.ts` emits `xr:visibility { visible: session.visibilityState !== 'hidden' }`, and only when that value changed. Not seen → the engine fades out over 0.2 s and suspends its context (as built), and `src/app.ts` calls `saver.flush()`. The event must come from the session's own listener: IWSDK copies `session.visibilityState` into `world.visibilityState` inside its render tick (`setupRenderLoop`), and a hidden session gets no tick, so that signal would show the pause only after it was over. Separately, the document's `visibilitychange` to hidden (a tab hidden or closing, with or without a session) → `saver.flush()` and nothing else. *Fails:* the write fails → the state stays pending and "Saving unavailable" shows when the user is back. Device: which of the three states the Quest Browser reports when the headset comes off and when the system menu opens (T-129, T-152). A blurred session counts as seen here: FR-SYS-05 names hidden only.

**G. Resume.** `visibilitychange` back → `xr:visibility { visible: true }`. The engine resumes; its clock stood still, so the tide carries on from its phase with no code of ours. `GardenSystem` applies a visit, which is saved like any change. *Fails:* the context will not run again → logged as `E_AUDIO_CONTEXT` (as built), the garden is silent; whether the Quest Browser wants a gesture for this is T-152's device question.
**Saving, all of it.** `src/app.ts` keeps the last state it saw. `garden:changed` → `saver.save({ ...state, settings: settings.get() })`. `settings:changed` → the same with the last state. `flush()` on `xr:visibility { visible: false }`, on `xr:sessionEnd`, and on the document's `visibilitychange` to hidden. `onSaveFailed` → the `E_SAVE_FAILED` caption, for 5 s. No system calls the saver.

**H. Session end.** Three.js fires `sessionend`; `src/app.ts` emits `xr:sessionEnd { visible: false }`, but only for a session whose start it emitted (Three.js can report an end with no start, as the code today notes). Each handler does its own part, and none depends on another's: `GardenSystem` sends back a seed that was out (`reason: 'reset'`) and forgets the signature; the engine fades and suspends; the page shows again with the focus on Enter; `RoomSystem` cancels the solver, hides the bed and removes `BedAnchor`, on which `BedRenderSystem` clears the plants and their targets; `HandSystem` detaches its sampler; `GardenAudioSystem` empties the engine's plants; `src/app.ts` flushes. An undo token that was alive is left to run out.

**I. Entering again.** B again: `engine.init()` only resumes (as built). Then C to E: the bed is placed anew, or comes back from its anchor (T-162); the signature is computed from nothing (FR-ROOM-13); the visit adds one to `visits` and issues no starter seeds; the plants are back the moment the bed is. Nothing made in step A5 is made twice.

**J. First launch, a restored garden, a corrupt save.**

### 3.4 One frame
IWSDK's loop, once per frame (`setupRenderLoop`): it copies the session's visibility into `world.visibilityState`, calls `world.update(delta, time)`, runs the `world.onXRFrame` callbacks (Roomsong registers none) and calls `renderer.render`. `delta` and `time` are seconds; a Roomsong system passes `time × 1000` wherever a call wants a frame time in ms that never goes back.

| Order | Who | Calls, every frame |
|---|---|---|
| 1 | `PerfSystem` (−100) | notes the frame's start time |
| 2 | IWSDK (−5 to 1) | input (moves `player.head`), UI, grab, scene understanding, transforms, layers |
| 3 | `RoomSystem` (10) | with an XR frame: `setFrame(frame, space)` on the three adapters. While *placing*: `solver.update(head, ms)`; at level 3 the ghost eases to `solver.preview()`. In the frame after the solver resolved: the placed step, with `room:bedPlaced`, `room:features` and everything their handlers do (sequence D) |
| 4 | `HandSystem` (20) | `sampler.setFrame`; per hand: `sample`, `HandState`, the hover, `machine.update`. Any `gesture:*` it emits is handled before step 5: the reducers run, and a `garden:changed` reaches audio, the renderers and the saver inside this call |
| 5 | `GazeDwellSystem` (25), `OnboardingSystem` (35) | when built |
| 6 | `GardenAudioSystem` (40) | `engine.setListenerPose(head)` |
| 7 | `SeedSystem` (49) | the seed's `worldPos` follows `HandState.palmPos`, or the carrying hand's `pinchPos` |
| 8 | `BedRenderSystem` (50) | `plants.update(phase, ms)`, `tide.update(phase, ms)` |

Targets are one frame old when hands reads them: `HandSystem` picks in step 4 against the `worldPos` written in steps 7 and 8 of the frame before. At 0.2 m/s that is under 3 mm for the seed on a moving palm; plants do not move.
The audio is not in this table: the engine's own 25 ms timer schedules the notes (§5.3), and a frame only moves the listener.

**Never per frame.** Each of these costs an allocation or a full rewrite, and has its own trigger:
- `plants.setState`, `engine.syncPlants`, making or moving a plant's target: on `garden:changed`, and when the bed is placed or moved.
- `engine.setSignature`, `roomSignature`, `applyVisit`: once per session, the visit once more per return from a pause.
- `RoomFeatureExtractor.extract`: once per placement. `PlaneAdapter.read()` outside it: only while levels 1 and 2 wait, at most 3 s per placement (the exception recorded in D-034).
- `saver.save`: on a change, and it writes at most once per `SAVE_DEBOUNCE_MS` (500). `saver.flush`: on hide and at session end.
- `bus.on`, `once` and `off`, `world.registerSystem`, `createEntity`, `guard.claim`: at set-up or on a change.
- Redrawing the caption's canvas: once per caption (as built).
- `log.debug` and `log.info`: nowhere in an `update`.
`solver.preview()` is called per frame during level 3 and must hand back one reused object.

## 4. Gesture state machine (`hands/GestureMachine.ts`)

`HandSystem` samples its `InputSource` once per frame for each hand it reports (API_SPEC §1.4) and feeds the `HandFrame` to the machine. The machine cannot tell WebXR hands, IWER's emulated hands and a pointer apart (§11). As built (T-116), `HandSystem` builds its own `HandSampler` and does nothing outside an XR session: no source is injected yet, and the garden window (T-114) adds the way to give it another one.

```
IDLE ──(pinchStart & target=plant)──► PINCHED(plant)
IDLE ──(pinchStart & target=seed)───► CARRYING(seed)
IDLE ──(pinchStart & target∈{orb,undo,panel})► PRESSED(target)
IDLE ──(palmUp 400ms & seedsAvailable)► DELIVER(seed→palmPos) ──► IDLE
IDLE ──(palmsOut 1.5s)──────────────► LISTEN
LISTEN ──(wake 600ms | pinchStart)──► IDLE
PRESSED ──(release, hover = pressed target)► IDLE  (release 'press', target: the petal undoes, a control acts; the Listen orb ──► LISTEN)
PRESSED ──(release anywhere else)───► IDLE  (release 'press', target null: nothing happens)
PINCHED ──(|d|≥2cm & |dy|≥|dxz|)────► PULLING
PINCHED ──(|d|≥2cm & |dxz|>|dy|)────► DRAGGING
PINCHED ──(release, |d|<2cm)────────► IDLE  (release 'none': no-op)
PULLING ──(release)─────────────────► IDLE  (release 'pull', dy: garden sets the height; the plant never moves)
DRAGGING ──(release, zone=bed)──────► IDLE  (release 'drag', cell = the hovered free cell: garden moves the plant)
DRAGGING ──(release, zone=inner)────► IDLE  (release 'drag', cell null: the plant returns to its origin cell)
DRAGGING ──(release, zone=outer)────► REMOVE → spawn UNDO petal at the release point (5 s)
CARRYING ──(release, zone=bed)──────► PLANT (release 'carry', cell = the hovered free cell) ──► IDLE
CARRYING ──(release, zone≠bed, or bed full)► seed returns to supply ──► IDLE
HELD ──(tracked=false)──────────────► HELD, frozen  (emit hands:lost; the grace starts)
HELD, frozen ──(tracked=true <200ms)► HELD          (emit hands:found; the gesture continues)
HELD, frozen ──(200ms elapsed)──────► IDLE          (emit gesture:trackingLost; revert)
```
`HELD` = any of PRESSED, PINCHED, PULLING, DRAGGING, CARRYING. `d` = pinch point − pinch origin in bed-local space; `dy` is its vertical part, `dxz` its horizontal part. `release 'x'` is the `gesture` field of `gesture:release`. Once it has arrived, a delivered seed rests at `HandFrame.palmPos` and follows it with no smoothing; the picker sees it there as an ordinary `Interactable`.
`zone` = `bedZone(bedLocalXZ)` from `garden/snap.ts`: `inner` if `len < R_in − 0.03` (< 0.09 m), `outer` if `len > R_out + 0.05` (> 0.35 m), else `bed`. With the bed centre at 0.45 m the `outer` zone starts 0.80 m from the head on the far side, which is beyond the 0.75 m reach cap; it starts 0.57 m away to either side and 0.10 m away on the near side. So a plant is removed by dragging it off sideways or towards the body, and the remove hint points that way (UX); the far side is never the only way.

**Commit on release (FR-HND-16).** Nothing changes the garden before a pinch ends. While a plant is held, `gesture:pull` and `gesture:drag` only drive previews (render, and the quiet audio preview). `gesture:release` is the one event that commits, and it says what ended: `gesture` = `press`, `carry`, `drag`, `pull` or `none`, with the committed `target`, the `cell` (carry and drag only, already resolved to a free cell by the hover below) and `dy` (pull only: the total vertical travel since pinch start). The full table is in API_SPEC §1.4. Garden acts on `gesture` alone. A pull release carries `cell = null`, so a pulled plant whose hand drifted sideways cannot be moved; its new height is `heightAfterPull(height, dy)` (FR-HND-08, in `garden/`), the same function the preview uses, so the height shown while pulling is the height that is saved. Discrete actions (planting a carried seed, the Listen orb, the undo petal, a panel control) take effect on release over the hovered target, never on pinch start; moving off the target before the release cancels. In the frame of a release the hover is updated first, then the release is evaluated.

**Dominant axis (FR-HND-08/10).** Inside the dead zone (`|d| < DRAG_DEAD_ZONE_M`, 2 cm) a pinched plant does not react. On the first frame outside it the larger part of `d` decides: `|dy| ≥ |dxz|` → PULLING, otherwise DRAGGING. The choice is latched until release, so a pull never turns into a drag. A tie goes to PULLING, the gesture that cannot remove a plant. Provisional until the device pinch test (T-105).

**Hover (FR-HND-16, `hands/TargetPicker.ts`).** Every frame, for each tracked hand, the picker finds what a pinch would act on.
- *Empty hand:* the nearest `Interactable` within that target's own radius (at least `HIT_RADIUS_M`, 4 cm; nearest wins; API_SPEC v1.2.3). The current target is kept until another candidate is at least `HOVER_DEAD_BAND_M` (0.5 cm) closer, and it is dropped once it is further away than `HIT_RADIUS_M + HOVER_DEAD_BAND_M`, so the highlight cannot flicker between neighbours or at the edge of the radius.
- *Carrying a seed or dragging a plant:* the cell a release would commit. The picker snaps the pinch point (`snapToCell`, with the same 0.5 cm dead band between neighbouring cells) and then resolves it with `nearestFreeCell(state, cell, draggedPlantId)`, using the plants of the latest `garden:changed`; a dragged plant's own cell counts as free. The cell is `null` when the zone is not `bed` or the bed is full.

`target:hover { hand, target, cell }` is emitted only when the choice changes; render draws the cell ghost or the plant glow from it. The ghost therefore shows the cell that will get the plant, also when the cell under the hand is occupied, and `gesture:release.cell` is that hovered cell, not a fresh snap. The hover is frozen during a tracking-loss grace and cleared (`target: null, cell: null`) when the grace expires or an empty hand is lost.
*As built (T-116):* the memory is an argument of the two pure functions `pickTarget(…, kept)` and `stickyCell(point, kept)`, and the machine keeps what they returned. Between two cells the dead band is measured to the cell centres: the remembered cell stays until the new one's centre is 0.5 cm nearer. There is no band at the edge of the bed: outside the `bed` zone the cell is `null` at once, as `gesture:release.zone` is. The ghost is to be the hovered cell's own marker drawn stronger (`render/BedRenderer.ts`, no extra draw call; T-119, not built yet). A carried seed hovers a cell and no target; a held plant hovers no cell until the drag of T-146.

**Tracking loss (FR-HND-15, NFR-REL-02).** The moment `HandFrame.tracked` goes false, `hands:lost { hand, held }` is emitted, once; `hands:found { hand }` is emitted once on return. render and ui show the tint and the hint only for a hand that held a gesture when it was lost, until `hands:found` and for at most 5 s; an empty hand shows neither (UX §3.4, D-030). A held gesture is frozen at the last pinch point for `TRACKING_GRACE_MS` (200 ms; tunable 150–250). Tracking back inside the grace: the gesture continues from the new sample (a pinch that opened meanwhile is an ordinary release). Grace expired: `gesture:trackingLost { hand }`, the state returns to IDLE and the in-flight change is reverted: a dragged plant lerps back to its cell over `REVERT_LERP_MS` (150 ms), a pulled plant returns to the height it had at pinch start, a carried seed returns to the supply, a pressed target is cancelled. Nothing is committed before release, so the garden model needs no undo and cannot be left half-changed. Pose timers (palm-up, palms-out, wake) restart when a hand is lost.
*As built (T-116; exact rules in API_SPEC §1.4):* `hands:lost` carries `held`, what the hand holds (`null` for an empty hand or a pinch on nothing), so "held a gesture" is `held !== null` for every consumer. `held`, and the `target` of `target:hover`, are the machine's own objects, reused from one event to the next: a listener copies what it keeps (with the `eventLog` flag the log shows the latest values for every logged hover). While a hand is untracked its `select` is held, as its `pinch` is (`HandSampler`), so a select that the platform ends during a one-frame dropout does not release what the hand still holds when it is back; whether a headset ends it is unverified. The machine's time is IWSDK's frame time in whole milliseconds, which never goes back; core's wall clock is read only for the caption's `expiresAt`. The grace is counted from the first untracked sample, and it also ends on a tracked sample that comes too late (a paused page delivers no samples in between): `gesture:trackingLost` first, then `hands:found`. A session that ends reverts a held gesture the same way (`GestureMachine.reset()`), so no consumer is left with a preview. The 5 s limit is `HAND_HINT_MAX_MS` in `hands/config.ts`. `HandSystem` (priority 20) raises the hint as a caption on the hand's own entity (`STRINGS.handOutOfView`) and takes it back on `hands:found` or at the limit; render is to dim a held plant for the same time (`PlantRenderer.setTint`; T-119, not built yet). The revert path of what does not exist yet hangs on the same event: a dragged plant's glide over `REVERT_LERP_MS` (T-146) and a carried seed's way back to the supply (T-127, T-128) start on `gesture:trackingLost`.

**Pinch signal (FR-HND-02; the T-124 rule).** An `InputSource` reports two booleans and the machine uses each for one kind of action.
- `HandFrame.select`, the tap signal, is the platform's own pinch classifier: true from `selectstart` to `selectend` of that hand's input source. Discrete actions use it: a pinch on a seed, the Listen orb, the undo petal or a panel control, and a pinch on nothing (wake), start and end on `select`.
- `HandFrame.pinch`, the hold signal, is ours: the thumb-tip to index-tip distance with hysteresis (pinch below `PINCH_ENTER_M` = 2.0 cm, release above `PINCH_RELEASE_M` = 3.2 cm), each edge confirmed over `PINCH_DEBOUNCE_FRAMES` (2) consecutive samples (27.8 ms at 72 Hz), with no new pinch for `PINCH_LOCKOUT_MS` (130 ms) after a release. The lockout applies to `select` as well; hysteresis and debounce do not, because the platform has done its own. A pinch on a plant starts and ends on `pinch`: it can become a pull or a drag, that is not known when it starts, and both are continuous holds whose release point is ours to place.

The hovered target at the moment a pinch starts decides which signal it uses, and its release is the falling edge of that same signal. This is the rule of the T-124 card and of plan v2.1 ("`selectstart`/`selectend` for discrete pinch, joint distance only for continuous pull"); the v1.2 draft's "OR the two signals" is *Cut*. A source with no platform classifier reports `select = pinch`: the pointer, where both are the button, and any XR session that delivers no `select*` for hands. Both signals are made inside the `InputSource`, not in the machine. Raw joints only: IWSDK grab components are not used (plan v2.1; grab under hand tracking is a known IWSDK issue, research §9.2). Provisional until T-105. Not verified: Meta's hands page says a pinch is exposed as a button press on the hand's emulated gamepad and does not mention `select*` (https://developers.meta.com/horizon/documentation/web/webxr-hands/); what the Quest Browser and IWER deliver is checked with `hz-quest-verify-first` before T-124 codes it.

Removed by the re-plan: TWISTING (wrist twist, FR-HND-09 cut) and the velocity-based flick → PRUNE (FR-HND-11 is now a drag-off release; no velocity threshold, so hand jitter at release cannot trigger it).
Replaced by plan v2.1 (D-021): the single rule `ANY ──(tracking lost >300ms)──► IDLE` (now the 200 ms grace above) and the per-axis thresholds `|dy|>2cm & |dxz|<2cm` (now the dominant-axis rule). Added: PRESSED, so the orb, the undo petal and panel controls commit on release.
All thresholds live in `hands/config.ts` (tunable via flags for device tuning sessions).

## 5. Core algorithms

### 5.1 Snap (`garden/snap.ts`) — annulus bed
Constants: `R_IN = 0.12`, `R_OUT = 0.30`, `RINGS = 5`, `STEPS = 16` (ring radii 0.12 / 0.165 / 0.21 / 0.255 / 0.30 m; ring gap 4.5 cm; inner-ring step spacing 2π·0.12/16 ≈ 4.7 cm, outer ≈ 11.8 cm; 80 cells).
```
local = inverse(bedPose) * worldPos                       // bed-local, y up
len   = length(local.xz)
zone  = len < R_IN − 0.03 ? 'inner' : len > R_OUT + 0.05 ? 'outer' : 'bed'   // off-bed if ≠ 'bed'
t     = clamp((len − R_IN) / (R_OUT − R_IN), 0, 1)        // 0..1 across the annulus
ring  = round(t * (RINGS − 1))                            // 0..4 (0 = inner ring, low pitch)
θ = atan2(local.z, local.x); step = mod(round(θ / (2π/STEPS)), STEPS)
```
Frame (D-029): bed-local +x points to the seated user's right, +y up, +z from the bed centre toward the user. So step 0 is at +x and the steps advance toward +z, clockwise seen from above: step 4 nearest the user, step 8 left, step 12 farthest.
`snapToCell` returns `null` when `zone ≠ 'bed'`. Occupied → BFS to nearest free cell (ring±1, step±1 first): `nearestFreeCell`, which the picker applies while the hand is still hovering (§4), not after the release. `undoRemove` uses it too: a plant whose cell was taken in the meantime comes back on the nearest free cell (D-031).

Target numbers (`hands/config.ts`; provisional until the on-device pinch-accuracy test T-105 / TC-DEV-00):
| Constant | Value | ID | Meaning |
|---|---|---|---|
| `TARGET_VISIBLE_DIAMETER_M` | 0.025 m | FR-HND-04 | drawn size of a cell marker and of a plant's base |
| `HIT_RADIUS_M` | 0.040 m (tunable 0.035–0.040) | FR-HND-04 | pick radius around an interactable; the nearest one wins |
| `HOVER_DEAD_BAND_M` | 0.005 m | FR-HND-16 | a new hover candidate must be at least this much closer |

With a 4.5 cm ring gap and 4.7 cm inner-ring spacing, neighbouring hit spheres overlap by design: "nearest wins" plus the dead band is what separates them, and the 4 cm radius is nominal there (between two inner-ring neighbours a target captures about 2.3 cm to each side). `snapToCell` stays the pure nearest-cell function, with no memory. The dead band and the resolution to a free cell live in `hands/TargetPicker.ts` (§4, Hover), and a release commits the hovered cell (`gesture:release.cell`), not a fresh snap, so the cell that was highlighted is the cell that gets the plant, also when the cell under the hand is occupied.
Two geometry decisions wait for T-105: (a) cell size: if the inner ring's 4.7 cm spacing scores below 90 % first-try, the fallback is 12 steps (inner spacing 6.3 cm) with the same 5 rings; (b) outer radius (D-020): `R_OUT` stays 0.30 m unless the outer ring scores below 90 % first-try or the bed does not fit the IWER VR-Glasses FoV mask when looking at the centre; then `R_OUT` = 0.25 m and the ring gap becomes 3.25 cm.

### 5.2 Pitch (`audio/theory.ts`)
`semitone = keyRoot + MODE_DEGREES[mode][ring]` with `ring ∈ 0..4`; `hz = baseHz(voice) · 2^(semitone/12)`. Five rings = five degrees = one pentatonic octave; no octave folding is needed because every set has exactly `RINGS` degrees.
Modes (D-025; `MODE_DEGREES` in `garden/model.ts`): `majorPent = [0,2,4,7,9]`, `minorPent = [0,3,5,7,10]`, `susPent = [0,2,5,7,10]`. All three are anhemitonic (no two degrees a semitone apart), so plants on adjacent rings cannot clash. `dorianHex` and `lydianHex` are *Cut (D-025)*: their first five degrees contain a semitone.
`keyRoot` is a semitone offset in −3..+4 (A = −3, C = 0, D = +2, E = +4) so the register never drifts more than a major third from C. `mode`/`keyRoot` come from the room signature (§5.8); Wanderer = C majorPent.
Room chord = `chordDegrees(mode)`, a mode-specific triple of ring indices (API_SPEC §1.1), so each mode has its own consonant chord:
| mode | ring indices | semitones | chord on C |
|---|---|---|---|
| `majorPent` | [0, 2, 3] | 0, 4, 7 | major triad, C–E–G |
| `minorPent` | [0, 1, 3] | 0, 3, 7 | minor triad, C–E♭–G |
| `susPent` | [0, 2, 3] | 0, 5, 7 | sus4, C–F–G |

Root and fifth are common to all three; the middle note tells the modes apart. These are the tuning-ripple notes (`AudioEngine.chordTone(0 | 1 | 2)`) and the UI confirm chord. The v1.1 chord "degrees 0, 2, 4" is *Cut (D-025)*.
Octave shimmer (plants ≥ 3 days old, §5.4): the old plan reserved a sixth scale degree for it, and the pentatonic sets have none. The shimmer is now the plant's own note one octave up (`semitone + 12`), mixed in at the §5.4 gain. An octave of a scale note is always in the scale, so it cannot clash and needs no extra degree.
Base octaves: Bass C2, Pad/Choir C3, Pluck/Bell C4, Shimmer C5.

### 5.3 Scheduler (`audio/Scheduler.ts`)
"Two clocks" pattern: `setInterval` 25 ms → while `nextStepTime < ctx.currentTime + 0.12` → for each plant at `step`, the pool assigns a voice channel (§7.1) and `voice.trigger(timeAt, params, channel)` → `nextStepTime += stepDuration`. Tide render position = `(ctx.currentTime − barStart) / barDuration`.
As built (T-121): step times are computed from an anchor, not summed, so they do not drift; a tempo change keeps the time of the next unscheduled step and does not move the tide phase. A step is counted before its listener runs, so a trigger that throws loses that step and not the clock. **Late steps:** after a stalled or throttled tick the scheduler walks every missed step, and the engine plays only those less than `LATE_DROP_S` = 0.1 s late; the older ones are skipped instead of sounding in one burst.

### 5.4 Growth (`garden/growth.ts`)
`ageDays = (state.lastVisitAt − plantedAt) / 86400e3`; stage = 0 (<1), 1 (<3), 2 (<7), 3 (≥7), a boundary belonging to the higher stage (`stageFor`). A plant's age is read from `lastVisitAt`, not from the live clock, so it changes only on a visit: `applyVisit` (API_SPEC §1.1) sets `lastVisitAt = max(now, lastVisitAt)` and returns one delta per plant whose stage rose, and GardenSystem emits `garden:grown` with them for the bloom animation. `lastVisitAt` never goes back, so a clock set back shrinks nothing. Octave shimmer gain = `min(1, (ageDays − 3) / 4)` for ≥3 days, from the same age.
The same call issues the seeds (FR-MUS-08): the starters on the first visit (`visits` 0, a garden from `newGarden`), afterwards one seed per local day visited, while the supply is below `SEED_SUPPLY_MAX`. The local date comes from `now` and the zone offset GardenSystem passes in; `garden/` reads no clock and no zone.

### 5.5 Placement (`room/PlacementSolver.ts`)
Returns `Promise<BedPlacement>` (API_SPEC §1.3); runs levels with timeouts (L1+L2 3 s combined, L3 10 s, L4 immediate). Each level emits `room:placementLevel` for UI and logging. Clamp (FR-ROOM-03, D-020; constants in `room/config.ts`): the bed centre targets `BED_CENTRE_DEFAULT_M` = 0.45 m forward of the head, which puts the far edge (centre + R_OUT) exactly on the `BED_FAR_EDGE_MAX_M` = 0.75 m reach cap. The centre may sit nearer, down to `BED_CENTRE_MIN_M` = 0.35 m, when the surface does not reach 0.45 m; it never sits beyond `BED_CENTRE_MAX_M` = 0.45 m. If the chosen surface point is outside 0.35–0.45 m, move it along the head→point vector into the range, to 0.45 m when beyond and to 0.35 m when nearer, while staying on the surface polygon when possible. L4 floating: 0.45 m forward, 0.25 m below eye height. (The v2 default of 0.40 m is replaced, D-020.)
Which surface, and which point of it (FR-ROOM-01, D-034; as built in T-123). A plane is read as the rectangle around its polygon, from its pose alone: the sign of its normal, `plane.orientation` and `lastChangedTime` are never read (tests/e2e/README.md). It is level when its normal is within 5° of vertical, either way up (`LEVEL_MIN_COS` = 0.996; provisional until T-129). The default spot is 0.45 m forward of the head, where forward is the level direction square to the head's right vector and every distance is measured level. The chosen surface point is the rectangle's point nearest the default spot. Reach rule: the plane counts only when that point is in front of the user and at most `BED_FAR_EDGE_MAX_M` = 0.75 m from the head, so part of the bed always rests on the surface. (*The centre-within-1.2 m rule and `SURFACE_MAX_DISTANCE_M`: replaced, D-034. It refused a long table from its short end and took a side table the bed could not touch.*) The centre then goes along the head→point line as far as the surface goes, held to 0.35–0.45 m, and takes the surface's own height there. Of several planes that count, the one whose point is nearest the default spot wins; the first seen wins a tie. Two height guards: a plane, or a level-3 hit, less than `FLOATING_DROP_M` = 0.25 m below the eyes is not used (no bed higher than the floating one would be: a level gaze meets a wall at eye height), and a level-3 hit lower than `SURFACE_MIN_HEIGHT_M` = 0.5 m above the floor is not a confirm (the floor is out of seated reach); the wait then runs on to the floating bed. Known limit: with the table to the user's side the bed is aimed at the table's nearest point, so it can land a few centimetres beside the table (5 cm with the edge 0.3 m to the side) although the table has a point 0.45 m away; a user who faces the table never meets it (device check, T-129). Per-frame cost: levels 1 and 2 read the planes anew on every frame of their wait, at most 3 s per placement (accepted, D-034).
Orientation (D-029): at every level the solver turns the bed about the vertical so that bed-local +z points from the bed centre toward the user (the head position at placement, projected onto the bed's plane), +x to the user's right and +y up. Step 0 is then on the user's right and step 4 nearest the user (§5.1).
Anchors (Must, D-021; FR-ROOM-07). The save holds a pair: `anchorHandle` and `anchorLevel`, the placement level the bed had when the anchor was made. A restored anchor gives back a pose and nothing else, and the chain that would report a level does not run. Without a saved level a returning session would have to be treated as level 3 or 4, which is Wanderer: the room signature would be gone from the second day on.
Order (RoomSystem; the same list as API_SPEC §1.3):
1. RoomSystem takes the saved pair from the state of the latest `garden:changed`.
2. In the session's first `update`, after `setFrame`, with a pair → `restore(handle, ANCHOR_RESTORE_TIMEOUT_MS)`. A pose within reach (D-041) comes back → `BedPlacement { pose, level: anchorLevel }`, `room:placementLevel`, `room:bedPlaced { restored: true }`.
3. No pair, unsupported, `null` or timeout → the chain, then `room:bedPlaced { restored: false }`, on which GardenSystem drops a stale pair. `create(pose)` then runs in the background (it has the old anchor deleted itself), and in the `update` after it gives a handle `room:anchored { handle, level }` lets GardenSystem store the new pair (`setAnchor`); the normal debounced save writes it. `create` gives `null` when no anchor could be made, and nothing is emitted then. Creating the anchor never delays the ripple or the first sound. A `create()` that is still on its way when the bed is placed again gives `null`: the next `create()` replaces it.
4. `RoomFeatures.extract(placement)` runs in both cases and reads the planes itself (§5.8).

Re-place from Settings (FR-ROOM-05) is step 3 again. The garden is kept in every case. One persistent anchor is kept per site: `create()` has the old one deleted before it makes the new one and sweeps every other one afterwards, so `clear()` before it is allowed and not needed. The Quest Browser allows a site 8 at a time (Meta, WebXR mixed reality: https://developers.meta.com/horizon/documentation/web/webxr-mixed-reality/). Restore reliability is validate-first on device (T-129, A1).

As built (`room/AnchorStore.ts`, T-162; the contract and every `null` case: API_SPEC §1.3):
- **Frames.** `frame.createAnchor` and `frame.getPose` work only inside the frame's own callback, and a promise continuation runs after it. The store therefore takes `setFrame(frame, space)` in every XR frame, like the adapters, and does both calls in there: a `create()` leaves its anchor call for the next `setFrame`, and a `restore()` is resolved by the `setFrame` in which the anchor first has a pose. No other method needs a frame, and none reads one in a continuation.
- **The pose is read once per call.** `restore` gives the anchor's pose in the session's reference space at the first frame that has a usable one, and the bed stays there until the room system asks again. The pose is handed on once per placement: `room:bedPlaced` carries it, the room features are read from it, and the plants' audio positions are set from it (`syncPlants` runs on `garden:changed` and `room:bedPlaced`, not per frame). Hands are the exception: `HandSystem` reads the bed entity's `matrixWorld` in every frame and would follow a bed that moved. A bed placed by the chain is fixed in the same way. Not tracked for a few frames at the start: the wait goes on, for at most the 4 s. Not tracked later in the session: nothing reads the anchor then, so nothing happens. The price: if the headset shifts its reference space during a session, the bed shifts with it, as a chain-placed bed does. The store keeps the session's anchor, also the one a `create()` made, so the room system can read the pose again with `restore(sameHandle)` and no call to the device: after a recentre, and after a pause. Following the anchor in every frame would change the bed-pose contract (API_SPEC §1.10 rule 5) and waits for a device to show the drift (T-129).
- **A pose becomes an anchor** through `XRRigidTransform`, which takes a position and a quaternion: the store turns the pose's rotation into one. It refuses a pose that is not rigid, and a mirror image: unit, square axes whose triple product is negative pass the rigidity check of `room/RoomFeatures.ts` and have no quaternion.
- **Order of a `create()`.** The delete of the old handle is asked for first, so its place among the site's anchors is asked free before a new handle is asked for; the answer is not waited for, and at least two frames pass before the handle request (the anchor is made in the next frame and arrives with the one after). A delete that fails changes nothing: the new anchor is made. With the new handle in hand comes the sweep: every other entry of `session.persistentAnchors` is asked to be deleted, which also takes an old anchor whose delete was refused, a handle that arrived after its session had ended, and whatever else was left on the origin.
- **Time-outs.** `restore` takes its own (`ANCHOR_RESTORE_TIMEOUT_MS`, the 4 s of FR-ROOM-07). That timer is stopped while the session is hidden and started anew, in full, when it is seen again; the store listens to the session's `visibilitychange` for as long as a restore waits, and no longer. Without it a headset lifted during the wait gave `null` after 4 s without a frame, and the re-placement that follows a failed restore deleted the saved anchor: the place was lost to a pause. `create` gives up after `ANCHOR_CALL_TIMEOUT_MS`, and `clear` waits no longer than that for the device; no requirement gives that number, so it is the same 4 s. Those two are plain wall-clock timers.
- **One anchor on the site (D-040).** IWSDK's `SceneUnderstandingSystem` is off (`features.sceneUnderstanding: false` in `iwsdk.config.json`). When on, it registers the `XRPlane`, `XRMesh` and `XRAnchor` components, makes an entity with a hidden wireframe mesh for every detected plane and mesh, and keeps a persistent anchor of its own: at session start it restores the one whose handle it saved in `localStorage` (`iwsdk_scene_anchor_uuid`), makes and persists a new one when it has none or the restore fails, and never deletes one from the device (`@iwsdk/core` 1.0.1 has no call to `deletePersistentAnchor`). Nothing in `src/` uses any of it: the room adapters read `frame.detectedPlanes` and `frame.detectedMeshes` themselves, and the session features come from `xr.features`, which this flag does not touch. With the system off, every persistent anchor of the origin but the store's own is a stray, and the sweep may delete it. That includes the anchor the test page `proto/spike/` makes on the same origin.
- **Origins.** An anchor is kept per origin, like the save. GitHub Pages and the mirror are two origins: a garden and its place from one do not come back on the other, where the bed is placed by the chain.
- **A restored bed can be out of reach.** The store gives back the pose the anchor has, wherever the user sits today. Whether a bed that comes back farther than the 0.75 m reach is used or re-placed is RoomSystem's decision (T-128c); today nothing checks it.

### 5.6 Vines (`room/WallFinder.ts` + `render/VineRenderer.ts`) — Could (C4, D-021; was Should S2); the halo (`render/HaloRenderer.ts`) is the Must fallback and always shows
Find ≤2 vertical planes within 3 m, prefer those in front hemisphere. Path: Catmull-Rom from bed edge → wall base → up the wall 1.2–1.8 m with ±0.15 m lateral noise. Tube geometry built once per Listen entry (≤20k tris total); animated by a `growth` uniform.

### 5.7 1€ filter
Standard implementation (Casiez 2012); per-axis, on the pinch point; `ONE_EURO_MIN_CUTOFF_HZ = 1.0`, `ONE_EURO_BETA = 0.0`, `ONE_EURO_D_CUTOFF_HZ = 1.0` (FR-HND-03; β 0.0 replaces 0.007).
β is in Hz per m/s: the cutoff is `min cutoff + β · |speed|`. With β = 0 the cutoff does not rise with hand speed: the filter is a fixed 1 Hz low-pass (time constant ≈ 0.16 s), steady at rest and laggy in motion. The pinch point trails a moving hand by speed × 0.16 s: 3.2 cm at 0.2 m/s, more than half a ring gap (2.25 cm). These are the starting values of the filter's own tuning procedure (settle the jitter with the min cutoff first, then raise β until the lag goes). T-105 raises β on device and searches about 5–50: β = 10 leaves about 1 cm of lag at 0.2 m/s, β = 20 about 0.6 cm. The change is one constant. The old 0.007 was already inert at hand speeds (it added 0.0035 Hz at 0.5 m/s), so the emulator and any build made before T-105 run the fixed 1 Hz low-pass. A non-zero default would change sheet 6.2 and needs Parth's approval; it is left as an open decision.
The filter state is reset when a hand is found again after a tracking loss (§4), so the first sample passes through unfiltered.

### 5.8 Room signature (`room/RoomFeatures.ts` → `garden/signature.ts` → `render/TuningRipple.ts`) — Should (S1), ADR-005 (amended 2026-10-10), D-010, D-021, D-025
Gated on device evidence (T-104 spike, T-129 script): go/no-go at G2, and the default is to build it with the Wanderer fallback. Without that evidence the app ships Wanderer-only and the pure function stays for later. Built after the core payoff is green (plan v2.1).

**Features (`room/RoomFeatures.ts`, FR-ROOM-10).** Computed once, ≤3 s after session start. The extractor reads the planes and meshes itself, from the `room/` adapters (no extra XR feature requests). It does not depend on the PlacementSolver having run, so a session whose bed came back from an anchor (§5.5) gets the same features as one that ran the chain. Its inputs are the bed pose and the placement level; `surfaceId` is not read. The bed surface is the level plane that passes within 5 cm of the bed centre in height and lies nearest to it on the floor plan, then nearest in height. The centre may lie up to 0.30 m past the plane's edge (the bed's far edge less its centre, FR-ROOM-03), measured as a distance to the plane's rectangle: placement leaves the bed that far short of a table that starts beyond reach (D-034). One rule with and without an anchor, so both visits find the same table (T-140 review: with the id as a hint, an anchor-restored visit lost the table, and with it the tint and the starter set).
`tableHeight` = height of the bed surface above the floor (levels 1–2 only); `tableArea` = area of that plane's rectangle; `floorArea` = area of the floor plane's rectangle (the largest level plane within 0.2 m of the floor), else the area of the **footprint rectangle** of the wall planes (it needs two walls that are not parallel), else unknown; `wallCount` = number of upright planes with height ≥ 1.5 m, where planes parallel within 5° whose centres lie within 0.10 m of the widest one's line count once (a door plane in a wall is not a fifth wall); `ceilingHeight` = height above the floor of the highest level plane at least 1.8 m up (whichever way it faces; a sloped ceiling is not level and gives none); `largestWallWidth` = the widest such wall; `roomVolume` = `floorArea × ceilingHeight` when both are known, else the footprint rectangle of the global mesh × its vertical extent (a mesh less than 1.8 m tall, or with more than 1,000 hull corners, gives none), else unknown; `level` = placement level 1–4. Heights are measured from the floor plane's own height when there is one, else from y = 0.
The footprint rectangle is the minimum-area bounding rectangle of the points projected onto the floor: the smallest rectangle found over the edge directions of their convex hull (rotating calipers; once per session, off the hot path). It is not the axis-aligned box of the reference space. That box depends on the angle between the room and the way the user faces at session start: a square room read at 45° doubles in area, and in the review's check the kitchen fixture changed its root at a 4° turn. The features of a room must not depend on its yaw; a fixture room turned by 30° checks that (TC-SIG-03).
A measurement that is not finite or not greater than 0 is dropped. An unknown field is left out of the object, never set to `undefined`. The extractor emits nothing: the caller (RoomSystem, §3) emits `room:features` with the features and the extractor's `surfaces`.
**As built (T-140, 2026-10-12; run on fixture rooms only, no headset yet).**
- Areas are rectangles because that is what `PlaneAdapter` gives. Exact for a rectangular room and the same on every visit; an L-shaped floor reads too large (27 m² reads as 36, which moves the key from C to A). The upgrade is a polygon area in `PlaneAdapter`, a change to `RoomPlane` and so to API_SPEC first, if T-129 shows such floors.
- A plane with a number that is not finite, a pose that is not rigid, or a size or position beyond 100 m is dropped. `extract` never throws.
- `surfaces` (for the tuning ripple) is of the last `extract`: the ceiling and the nearest wall at every placement level, the table only at levels 1 and 2. A Wanderer session is therefore told by its signature, not by missing surfaces.
- The extractor cannot tell "no planes yet" from "no planes": on the anchor path the caller waits for planes, up to the 3 s budget, before it extracts.
- Cost on the development Mac: 0.01 to 0.03 ms for a 7-plane room; the mesh path about 25 ms for 50,000 vertices, once, and only when the planes give no volume. The hull step is quadratic in hull corners (26 ms at 2,000), hence the 1,000 limit.
- Known limits, to look at on the headset (T-129): with no floor plane, the floor from the walls appears only once two walls differ by more than 5°; three parallel planes 8 cm apart count as one or two walls depending on their widths; with no ceiling plane, the level top of a tall cupboard at 2.0 m reads as the ceiling.

**Signature v1 (`garden/signature.ts`, FR-ROOM-11, D-021).** In v1 the room moves exactly three things: the reverb decay, the key root and the mode. The tempo is a constant. Every other feature feeds only a hash. Each input is bucketed and the signature depends only on the bucket tuple, so detection noise never changes the song unless a value sits within noise distance of a boundary. Constants live in `garden/config.ts`. The steps, in order:

1. **Wanderer rule.** `level ≥ 3`, or no measured field known → the whole signature is `WANDERER` = `{ keyRoot: 0, mode: 'majorPent', tempo: 84, reverbRt60: 0.9, reverbSize: 'medium', starterVoices: [bell,pad,pluck], paletteSeed: 0 }` regardless of other fields. The same holds for a level that is not 1 or 2 at all (0, 5, a fraction, not a number) and for a missing argument (`null`, `undefined`): only level 1 and level 2 are a measured room. A value that is not finite or not greater than 0 counts as unknown here too, so the function is total. The result is then `WANDERER` itself, the same frozen object; every other signature is a frozen object too, its `starterVoices` included. At level 1 or 2 unknown fields take their default bucket (marked \*) individually, and one known field is enough for a room's own signature. The `forceSignature=wanderer` flag is not part of the function: GardenSystem checks it and then uses `WANDERER` without calling `roomSignature`, which stays pure.
2. **Reverb decay (FR-ROOM-06): Sabine's formula on the room volume, with a fixed absorption area.**
   ```
   V   = roomVolume ?? floorArea × (ceilingHeight ?? CEILING_DEFAULT_M)   // CEILING_DEFAULT_M = 2.7. No volume and no floor area →
                                                                          // reverbRt60 = REVERB_RT60_DEFAULT_S (0.9 s); go to step 3
   raw = SABINE_K · V / SABINE_ABSORPTION_M2                               // Sabine: RT60 = 0.161 · V / A
   reverbRt60 = the step of clamp(raw, REVERB_RT60_MIN_S, REVERB_RT60_MAX_S) in the table below
   ```
   `SABINE_K = 0.161` s/m. `SABINE_ABSORPTION_M2 = 10` m² is the one absorption constant: the room's equivalent absorption area A, held the same for every room. It is **tuned for an audible musical range, not for acoustic truth**. In a real room A grows with the surfaces, so the real decay grows only with the room's linear size, and with any single absorption coefficient homes differ by a factor of about 2.3. The v1.2 draft did exactly that (`A = 0.10 · S`): more than nine ordinary rooms in ten landed on 0.9 or 1.2 s, a 3 × 4 m bedroom and a 5 × 5 m living room both got 0.9 s, and neither 0.3 s nor 2.0 s could be reached in a home (2.0 s needed more than 150 m² of floor). With A fixed the decay is proportional to the volume (`raw = V / 62.1`) and homes use the whole clamp:

   | `reverbRt60` | 0.3 s | 0.6 s | 0.9 s | 1.2 s | 1.6 s | 2.0 s |
   |---|---|---|---|---|---|---|
   | room volume (m³, rounded; `raw` decides) | < 28.0 | 28.0–46.6 | 46.6–65.2 | 65.2–87.0 | 87.0–111.8 | ≥ 111.8 |
   | floor area under a 2.7 m ceiling (m², rounded; `raw` decides: 32.2 and 41.4 m² fall just below their boundaries) | < 10.4 | 10.4–17.3 | 17.3–24.2 | 24.2–32.2 | 32.2–41.4 | ≥ 41.4 |

   The same bedroom now gets 0.6 s and the same living room 1.2 s. The result does not predict the room's measured RT60, and the Devpost copy must not say it does. The draft's `SABINE_ALPHA` and its surface estimate `S` are *Cut (v1.2 review)*.
3. **Key root** from the floor-area bucket: a bigger room has a lower root (E, D, C, A).
4. **Mode** from the ceiling-height bucket. Not from table height.
5. **Tempo** = `DEFAULT_TEMPO_BPM` = 84 (`core/`). The room does not set it in v1.
6. **Hash** of the bucket tuple → starter voices and palette seed.

| Input | Buckets (unknown → default, marked \*) | Drives |
|---|---|---|
| `raw` RT60 (s), from `roomVolume`, or from `floorArea` and `ceilingHeight` | `< 0.45` → 0.3 · `0.45–0.75` → 0.6 · `0.75–1.05` → 0.9\* · `1.05–1.40` → 1.2 · `1.40–1.80` → 1.6 · `≥ 1.80` → 2.0 (= `REVERB_RT60_STEPS_S`) | `reverbRt60` |
| `reverbRt60` (s) | `< 0.75` → small · `< 1.05` → medium · else large | `reverbSize`: a derived label for the Settings UI. It sets nothing in audio (§7.1) |
| `floorArea` (m²) | `< 8` → E (+4) · `8–17` → D (+2) · `17–34` → C (0)\* · `≥ 34` → A (−3) | `keyRoot` |
| `ceilingHeight` (m) | `< 2.60` → minorPent · `2.60–2.90` → majorPent\* · `≥ 2.90` → susPent | `mode` |
| none | constant 84 | `tempo` |
| `tableHeight` (m) | `< 0.62` → 0 · `0.62–0.85` → 1\* · `0.85–1.00` → 2 · `≥ 1.00` → 3 | hash only |
| `tableArea` (m²) | `< 0.5` → 0 · `0.5–1.5` → 1\* · `≥ 1.5` → 2 | hash only |
| `wallCount` | `1–2` → 0 · `3–5` → 1\* · `≥ 6` → 2 (a count of 0 is unknown, like every value that is not above 0: it takes the default bucket) | hash only |

Named constants (`garden/config.ts`, each with a comment citing its ID): `SABINE_K = 0.161`, `SABINE_ABSORPTION_M2 = 10`, `CEILING_DEFAULT_M = 2.7`, `REVERB_RT60_MIN_S = 0.3`, `REVERB_RT60_MAX_S = 2.0`, `REVERB_RT60_STEPS_S = [0.3, 0.6, 0.9, 1.2, 1.6, 2.0]`, `REVERB_RT60_BOUNDS_S = [0.45, 0.75, 1.05, 1.40, 1.80]`, `REVERB_RT60_DEFAULT_S = 0.9`, `REVERB_LABEL_BOUNDS_S = [0.75, 1.05]` (all FR-ROOM-06); `ROOT_AREA_BOUNDS_M2 = [8, 17, 34]` with `ROOT_SEMITONES = [4, 2, 0, −3]`, `MODE_CEILING_BOUNDS_M = [2.60, 2.90]`, `TABLE_HEIGHT_BOUNDS_M = [0.62, 0.85, 1.00]`, `TABLE_AREA_BOUNDS_M2 = [0.5, 1.5]`, `WALL_COUNT_BOUNDS = [3, 6]`, `WALL_WIDTH_BOUNDS_M = [2.5, 4.0]` (all FR-ROOM-11). The tempo is `DEFAULT_TEMPO_BPM` from `core/` (FR-MUS-03). `garden/` exports no tempo constant. Its pure files may not load `core/` at run time (API_SPEC §1), so `signature.ts` repeats the number in one private constant typed as `typeof DEFAULT_TEMPO_BPM`: a different number in `core/` fails the typecheck, and a unit test compares the two.
Boundaries are half-open (`[lo, hi)`). `h = fnv1a32(rootBucket, modeBucket, rt60Step, tableHeightBucket, tableAreaBucket, wallCountBucket, wallWidthBucket)`: 7 bytes, each the 0-based index of its bucket in the table above, read left to right (FNV-1a 32-bit, offset basis `0x811c9dc5`, prime `0x01000193`; no floats enter the hash). None of the 7,776 tuples hashes to 0, so `paletteSeed` 0 always means Wanderer.
`starterVoices = STARTER_SETS[h % 6]` with `STARTER_SETS = [[bell,pad,pluck], [pluck,choir,bass], [bell,choir,bass], [pad,pluck,bass], [bell,pad,choir], [pluck,bell,choir]]`: six different sets, each with at least one sustaining voice (pad, choir) and one percussive voice (bell, pluck); index 0 is the Wanderer set. (The draft's sixth set repeated the fourth in another order.)
`paletteSeed = h` (uint32); the renderer derives a hue rotation `(h % 360)°` and a saturation nudge `((h >>> 9) % 3) − 1` applied to the fixed bioluminescent palette (UX §5).
The 12 (root, mode) pairs give 8 different sets of note names: C major, A minor and D sus are the same five notes, and so are E minor and A sus, and D major and E sus. Two such rooms still differ in which note sits on which ring, in the room chord and usually in the decay.

**Validate-first, not in v1 (D-021).** Table height → key or register, and anything → tempo. Neither has evidence that a listener hears the cause (research §8; note 06, KQ6); both wait for the stranger test H13 (UAT-17). Table height keeps its v1.1 buckets as a hash input, so switching a mapping on later needs no new feature. The v1.1 rows `tableHeight → keyRoot`, `floorArea → mode`, `wallCount → tempo` and `floorArea → reverbSize` are *Cut (D-021, D-025)*.

**Stability contract (TC-SIG-02).** The tolerance is ±5 cm on a length (heights, widths, each side of the mesh bounds) and ±0.3 m² on an area. It is a bound for the tests, not a measurement of the device.
*Bucketed inputs.* An input at least its tolerance from a boundary keeps its bucket. The narrowest buckets (0.15 m table height, 0.30 m ceiling height, 1.0 m² table area, 9 m² floor area) are ≥ 3× the tolerance. Ceiling boundaries sit between the usual build heights (about 2.4–2.5 m, 2.7–2.75 m and 3.0 m); floor-area boundaries sit between common room sizes (9, 16, 20, 30 and 36 m²). On a grid of 375 ordinary rooms (2.5–7 m × 2.5–8 m, ceilings 2.4–3.0 m) 1.3 % can change root at the worst corner of the tolerance.
*Wall count.* A count has no tolerance: one missed or doubled wall moves it by one. The default bucket is three wide (3–5), so a four-walled room keeps its bucket either way; a room detected with 3 or 5 walls does not. It feeds only the hash (the starter voices of a new garden, and the tint), never key, mode or decay.
*Reverb decay.* It is quantised after the formula, so its boundaries live in RT60 space (0.45, 0.75, 1.05, 1.40, 1.80 s), that is at volumes of about 28.0, 46.6, 65.2, 87.0 and 111.8 m³ (rounded; `raw` decides). The tolerance moves `raw` by 0.0161 s per m³. When the volume is area × height that is `0.0161 · (0.05·F + 0.3·H + 0.015)`: at most 0.024 / 0.028 / 0.035 / 0.043 / 0.052 s at the five boundaries (ceilings 2.2–3.5 m). When it is the mesh bounds with ±5 cm on each side it is at most 0.026 / 0.037 / 0.047 / 0.059 / 0.071 s (rooms up to 3:1). A room whose `raw` is further than that from every boundary keeps its step. On the same grid about 17 % of rooms sit within the worst-case tolerance of a decay boundary (the draft formula: 7.5 %, with two steps doing all the work). A flip moves the decay by one step, 0.3–0.4 s, and changes neither key nor mode.
*Which output is the least stable (T-141 review).* The mode, not the decay as this section said before. The grid above has ceilings only at the usual build heights, none of them near 2.60 m or 2.90 m, so it cannot show this. With ceilings spread evenly over 2.3–3.2 m, about 22 % of rooms sit within 5 cm of a mode boundary (two boundaries, 0.10 m each, out of 0.90 m). With room sizes spread evenly as well, about 19 % of rooms sit within the tolerance of a decay boundary and about 5 % within 0.3 m² of a root boundary. These figures count the rooms that **can** switch, not how often one will. If the error of every visit filled the whole tolerance, about 1 room in 14 would get a different mode on a second visit (the 22 % above; a third of them land on different sides when both errors are spread evenly over the tolerance). All of this is arithmetic on an assumed error and an assumed spread of rooms, not a measurement: the device run (T-129) measures the real drift between two sessions in one room.
Only the documented boundary case (an input within tolerance of a boundary) may flip, and TC-SIG-02 asserts that it does. Hysteresis across sessions is **not** in v1: it needs persisted features, and FR-ROOM-13 recomputes the signature from nothing each session. The noise expected between two sessions in one room is far below the tolerance: the Quest Browser's planes are the surfaces the user defined in the headset's room setup, which the browser exposes as planes (Meta, WebXR mixed reality: https://developers.meta.com/horizon/documentation/web/webxr-mixed-reality/), so the same room should repeat the same inputs until the user redoes the setup. ### 5.9 Flash cap (`render/FlashGuard.ts`, FR-UI-11)
No element changes luminance more than 3 times per second. The terms, with constants in `render/config.ts` (API_SPEC §1.8):
- **Element** = one drawn instance whose brightness is animated: one plant, one cell marker or ghost, one beat-ring tick, one ripple quad, the halo, the tide crest (its showing and hiding; its sweep keeps one brightness and relies on a continuous phase, API_SPEC §1.8). A shape that moves at constant brightness is not changing luminance; what it lights up is counted on the element it lights (the trigger flash, on that plant).
- **One luminance change** = one swing of the element's brightness factor (0–1, the multiplier its material applies) in one direction, of at least `FLASH_MIN_DELTA` = 0.10, measured from where the last swing ended. It is counted when it starts, the moment it can still be refused. A swing ends only when the brightness comes back at least `FLASH_MIN_DELTA` from its far end: a pause or a smaller step back does not end it (design no stairs). Before its first swing an element may move less than half of `FLASH_MIN_DELTA` from its claimed brightness. A refused swing holds the element where it is. A flash, up and back, is two changes. A slow fade counts once, like a fast one.
- **Cap** = at most `FLASH_CAP_PER_S` = 3 changes of one element in any sliding 1 s window. That is at most 1.5 full flashes per second, half of what WCAG's three-flashes rule allows (a flash there is a pair of opposing changes of 10 % or more), so NFR-ACC-01 holds with margin.

**Enforcement.** Animation code does not write a brightness directly; it asks FlashGuard to start a swing for an element. FlashGuard grants it when the element's window has room and otherwise holds the element at its current brightness until it has. FlashGuard counts from the values it hands out, so its report does not depend on the callers. `perf:sample.maxFlashPerS` is the largest count any element reached in the last second; TC-E2E-15 asserts it never exceeds 3 with `autoplant=80` in Listen mode. The beat ring (`access/`) and the hover cue go through the same guard; `access/` and `ui/` may import `render/`.
**Consequences.** Per-step effects are safe: the tide passes 5.6 steps per second at 84 BPM and 8.0 at 120, but each plant and each ring tick is hit once per bar, which is two changes in 2.9 s at 84 BPM. Anything that pulses on every beat makes two changes per beat: 2.8 per second at 84 BPM, 3.2 at 96, 4.0 at 120. Above 90 BPM such an element pulses on every second beat; that is a fixed rule, not a pulse dropped here and there. The hover cue is a level, not a blink.

## 7. Voice design (`audio/voices/`)
| Voice | Pri | Synthesis | Shape silhouette |
|---|---|---|---|
| Bell | M | 2-op FM (ratio 3.5, index decays), exp decay 1.5 s | Tall bulb with drooping cap |
| Pad | M | 3 detuned saws → LPF (cutoff from hue) → slow attack 0.4 s | Wide soft fan of leaves |
| Pluck | M | Karplus-Strong string (noise burst → delay line + LPF feedback), computed into an `AudioBuffer` (see below) | Thin reed with a bead |
| Bass | M | Sine + 0.8 × its 2nd harmonic, soft-clipped (tanh, drive 3). The clipped cycle is computed once into a `PeriodicWave` of 12 harmonics and one oscillator plays it → low-pass (cutoff 8 × the note, ±1 octave from hue) → envelope: 10 ms attack, hold 0.2 × release, decay τ = release ÷ 25. About 0.65 s for a new plant, 0.1 to 1.1 s over the height range; audible level in the 2nd and 4th harmonics (see below) | Low, broad bulb |
| Choir | M | 3 formant band-passes over a pulse, slow vibrato | Cluster of three rounded petals |
| Shimmer | S (S5) | Band-passed noise grains × 6, high register | Spiky star-burst |

Phase 0 desktop sound prototype (G0) uses Bell, Pad, Pluck only.

All voices expose `trigger(time, { hz, gain, release, cutoffMul, detune }, out)` and `dispose()`; `out` is the input of the voice channel the pool assigned (§7.1). `Voice` is internal to `audio/`.
**Pluck is not a live delay loop.** A feedback loop through a native `DelayNode` cannot be shorter than one render quantum (128 frames: 375 Hz at 48 kHz), and Pluck plays 220–587 Hz: 26 of its 60 pitches are above that. The string is computed by pure code into an `AudioBuffer` and played through an `AudioBufferSourceNode`, as in the T-102 prototype. Buffers are cached per pitch and damping bucket, not per plant: 5 ring pitches × `PLUCK_DAMPING_BUCKETS` = 4 gives at most 20 buffers of `PLUCK_BUFFER_S` = 1.6 s, about 6 MB at 48 kHz (one buffer per plant would be 25 MB at 80 plucks). No buffer is rendered in the call that needs it: `syncPlants` and a re-tune only ask for the strings of their plants and make their buffers, empty, and the engine's 25 ms tick renders `PLUCK_STRINGS_PER_TICK` = 2 of them, oldest first, before it schedules, so `setSignature` cannot stall a frame during the tuning ripple and a string asked for between two ticks is ready for the first note that needs it. Until a string is ready its notes play the nearest ready one, re-pitched with `playbackRate`: nearest by interval, and of two as near the one of the same damping bucket. The pitch is right from the first note and only the tone differs (a string played faster is brighter and shorter). A re-pitched source is stopped at the end of its buffer, `PLUCK_BUFFER_S` ÷ rate, where the string has its fade, and not inside it. If no string at all is ready, which a running engine never meets (the tick renders before it schedules) and a render test that triggers with no tick does, the note's own string is rendered on the spot. **As built (T-143).** A re-tune drops the strings of the old key and the ones still waiting, so a second signature drops the unfinished work of the first; the 20 strings of a key take 10 ticks, 0.25 s, and the reverb's impulse response follows in slices (§7.1). In Node on a laptop one string takes 0.23 ms, and the costliest tick of a re-tune about 0.6 ms where the call took 12.3 ms at once before (API_SPEC §1.2; no time is pinned by a test). A tick that renders makes no buffer and puts no sample on the heap (NFR-PERF-08): the buffer was made by the call, and the noise of a string and of a response is mulberry32 written out in the render loop, because a generator called once per sample handed back a float that the engine kept on the heap (321 000 bytes for a response slice; 1 000 to 1 400 now, and 250 to 365 for a string; a test pins each, and three sums over the samples pin the sound of a response and of two strings). The first string of a process is rendered by code the browser has not compiled yet and takes 4 to 5 ms, so `init()` renders one string to no buffer inside the Enter gesture (`Pluck.warmUp`); a browser may drop compiled code it has not run for minutes, and the next string then costs one tick of that size again; the remedy, if a device shows it, is to slice the string render by samples as the reverb's is. Not measured on a headset, and nobody has listened to a re-tune yet.
**Bass has to be audible on small speakers.** Its fundamentals are 55–147 Hz (ring 0: A 55, C 65, D 73, E 82 Hz), which a headset's speakers may not reproduce (not measured). The voice therefore carries audible level above its fundamental. As built (T-144), relative to the fundamental: 2nd harmonic −2.5 dB, 3rd −14.4 dB, 4th −8.0 dB (computed); the 2nd and 4th carry the note. Share of a note's energy above 120 Hz in a desktop Chromium render at the middle hue: 14.8 % for A1 (55 Hz, the one note whose 2nd harmonic is under 120 Hz), 46 % from 61.7 to 116.5 Hz, all of it from 123.5 Hz. Above 200 Hz: 12.5 to 14.7 % up to 98 Hz, 46 % above. Not heard on a headset; if A1 is weak there, `BASS_DRIVE` is the first lever, and the device audio test W1 (T-129) includes a bass-audibility check.

## 8. Error handling & recovery
- Each system's `update` is wrapped: catch → `log.error` → system disabled for 1 s → re-enabled (circuit breaker). The wrap is the `register` helper of §3.2, in `src/app.ts`, and it covers IWSDK's own systems too. It is what keeps the frames coming: nothing between a system's `update` and the browser's frame callback catches a throw, and Three.js asks for the next frame only after the callback has returned. Code the wrap cannot reach catches its own throw: a query's `qualify` or `disqualify` callback, a callback inside the render, and the start-up steps of §3.3 A (a throw there → `landing.failed()`).
- Audio context suspended (autoplay) → resume on first user gesture (Enter button already satisfies).
- Save failure → the same write goes to localStorage; still failing → in-memory only (the state stays pending, and the next `save()` or `flush()` tries again) + caption "Saving unavailable". PersistenceSystem calls `onSaveFailed` when writes start to fail, once per run of failures, and `src/index.ts` raises the `Caption` from it (§3); PersistenceSystem listens to no event and never calls `ui/` (API_SPEC §1.5, §2).
- IndexedDB that does not open within `IDB_OPEN_TIMEOUT_MS` (1.5 s) → the session runs on localStorage alone, so the start never waits for it. A garden already in IndexedDB is not shown in that session and is never overwritten without a backup (API_SPEC §4).
- Hand tracking lost → grace, revert and hint as in §4 (FR-HND-15); the garden model is never touched before a release, so there is nothing to repair.
- Anchor restore fails or anchors are unsupported → re-place by the chain, garden kept (§5.5, FR-ROOM-07).

## 11. Garden window and `InputSource` (FR-SYS-07, Should S6, T-114)
The headset-free bench and demo: the same garden in a plain browser tab. Never the judged path.
**Mode gate (`src/index.ts`).** `immersive-ar` supported and no `window` flag → the XR path. Otherwise → the garden window. The gate picks the `InputSource` (API_SPEC §1.4) and hands it to HandSystem; nothing else in the shared modules knows which mode it is in.

| | XR path | Garden window |
|---|---|---|
| Input | `hands/HandSampler.ts`: WebXR hand joints (IWER's emulated hands arrive through the same API, so they need no adapter) | `window/PointerSource.ts`: pointer or touch |
| Camera and stage | the XR viewer over passthrough | `window/WindowStage.ts`: one fixed camera at a seated eye point, aimed at the bed; a virtual table drawn under the bed |
| Placement | PlacementSolver chain L1–L4 | no XR adapter reports `supported()`, so the chain returns L4 at once; the camera stands in for the head |
| Signature | from the room, or Wanderer | Wanderer (level 4) |
| Lifecycle | XR session events | the same `xr:*` events, emitted for the page: Enter click, close, `visibilitychange` |
| Systems, garden, audio, save | §3 | identical |

**`PointerSource` → `HandFrame`.** One hand only (`hands` = the dominant hand). A mouse, a pen and a touch contact are all pointer events and get one mapping. No filter and no hysteresis: a button is already clean.
| Field | Value |
|---|---|
| `tracked` | true from Enter on, while the page is visible. Sticky: the source keeps the last pointer position, so a lifted finger, or a mouse that has left the canvas, is reported there with `pinch = false`. A touch lift is therefore a release, not a tracking loss. Before the first pointer event the position is a fixed spot beside the bed (WindowStage sets it). False only while the page is hidden |
| `pinch`, `select` | the same value: the primary button or a touch contact is down. **Latched:** pointer events are queued and `sample()` hands out at most one change per call, so a press and a release that both arrive between two frames are still seen, `true` in one sample and `false` in the next. A position jump that arrives together with a press (a touch landing somewhere new) is reported first, with `pinch = false`, and the press in the next sample, so the hover is computed at the new place before the pinch starts |
| `pinchPos` | where the camera ray through the pointer meets the bed plane. Every target of the window lies on that plane: plants, the Listen orb in the centre hole, the undo petal |
| `palmNormal` | world up, constant. A pointer has no palm; this keeps the palm-up pose true whenever the source is tracked, so the next seed is delivered 400 ms after the machine is idle (§4) |
| `palmPos` | the pinch point, while no plant, orb or undo petal is within `HIT_RADIUS_M` of it; otherwise the fixed spot beside the bed. A delivered seed rests at `palmPos` (§4), so it rides the pointer over open ground and steps aside when the pointer is on another target. Nearest-wins then picks that target, and the picker needs no special case |
| `velocity` | finite difference of `pinchPos` |

What a user does: click or tap an empty cell, and the seed riding the pointer is pinched and released there, so it is planted (TC-E2E-14). One `mouse.click()` is three samples (move, press, release) and so is a tap. Press a plant and drag to move it, drag it off the bed to remove it, click the undo petal to undo, click the centre orb to listen. Nothing needs a hover, so touch works like the mouse. After a plant the next seed arrives 400 ms later; a click before that does nothing.
Reach in v1: receive and plant a seed, drag to move, drag off to remove, undo, the Listen orb. Not reachable in v1: pull (a pointer on the bed plane has no vertical travel) and the settings panel (it opens from the settings orb at the wrist, which a pointer does not have; the landing page's access toggles are the settings of the window). Adding either later is a change inside `window/` only, with no contract change.
**Render path.** The same render systems and the same rendering rules (HLD §7, NFR-PERF-09). There is no XR layer, so the canvas's own antialiasing stands in for the XR layer's MSAA and there is no foveation. How the IWSDK world is created without a session is PoC U1, run first in T-114; nothing above depends on its answer.
