## 1. Module public interfaces (TypeScript)

**Dependency direction (v1.2).** `core/` imports no other Roomsong module; the only package it may import is `@iwsdk/core`, in `core/components.ts`. `garden/` imports only `core/`: its pure files (`model`, `rules`, `snap`, `signature`, `growth`, `config`) take plain types only (`import type`, so no IWSDK or Three.js code is loaded with them), and `garden/GardenSystem.ts`, the garden's state holder, a plain class and not an ECS system (§1.10), also uses core's bus, clock, flags, log and settings store. `room/`, `hands/`, `audio/` and `persistence/` import `core/` and `garden/`. `render/`, `ui/`, `access/`, `onboarding/` and `window/` may import any module named before them. Only `src/index.ts` (the boot) and `src/app.ts` (the wiring it loads, §1.10) import across all modules. An import goes through the other module's `index.ts`, with two rules that keep the SDK out of the boot chunk (§1.10 rule 1): every importer of the three shared components takes them from `core/components.js`, which `core/index.ts` does not re-export; and `src/index.ts` takes `mountLanding` from `ui/Landing.js`, because `ui/index.ts` also exports `CaptionSystem`. Nothing imports upward, and modules on the same level talk through the event bus (§2) or a shared component, never through imports.
**Shared ECS components.** A component has to be imported to be queried or attached, so a component that a module on the same level or a lower level uses is declared in `core/components.ts`: `BedAnchor` (room writes it; hands, render and audio read it), `Interactable` (render and ui attach it; hands and access read it) and `Caption` (any module raises one; ui is the only reader). Every other component stays with the module that writes it and is read only from above: today that is `HandState` in `hands/` alone. Fields: LLD §3.1. All of them are registered in `src/components.ts`, which imports each component from its own system-free file (`core/components.js`, `hands/HandState.js`) and not through a module's `index.ts`: an index may export systems, and the manifest is loaded by the editor and must stay free of them. Not components: `RoomSurfaces` is a plain type of `room/` that travels in `room:features` (§2); `PlantView` is *Cut (T-128 contract)*, nothing would read it; `VineTarget` belongs to the vines (Could, C4) and is not built.

**Runtime rules (v1.2.1).** `log`: without `Flags.dev`, debug and info are dropped before any work; warn and error always reach the console and the ring. `bus`: one function is one subscription per event, as with `addEventListener`; `on`, `once` and `off` allocate and never run per frame. `core/` builds `flags`, `log` and `clock` once, when it is first imported; every other module follows the `Flags` rule of §3.
**Strings.** `STRINGS` is the caption table: everything a `Caption.key` may name, at most six words each (FR-UI-01; tuning-ripple captions have their own smaller limits, LLD §5.8). The 2D page's copy lives in `ui/strings.ts` (§1.9). There is no user-facing text anywhere else, except the two things `index.html` must hold without a script: the page title and the `<noscript>` line.
**Axes (D-029).** Bed-local space: +x points to the seated user's right, +y up, +z from the bed centre toward the user; the PlacementSolver places the bed that way (LLD §5.5). A bed-local `Vec2` is the bed's horizontal plane: `x` = bed-local x, `y` = bed-local z. `snapToCell`, `bedZone` and `cellCentre` (§1.1) take and return that; the height is dropped before the call. Step 0 is at +x and the steps advance toward +z, clockwise seen from above: step 4 is nearest the user, step 8 on the left, step 12 farthest (`θ = atan2(z, x)`, LLD §5.1). `SurfaceRef.extents` (§1.3) is `x` = width, `y` = height in the plane's own space.

`chordDegrees(mode)` is mode-specific, so each room chord is a distinct consonant sonority. Root and fifth are shared; the middle note tells the modes apart.

Graph shape (LLD §7.1, NFR-PERF-10): 24 pooled `PannerNode`s with `panningModel = 'equalpower'`, exactly one `ConvolverNode` on a shared send bus with one send level for every room, behind one 200 Hz Butterworth high-pass (P-011), its impulse responses all of one energy (`IR_ENERGY`, `normalize = false`, P-022: one wet level in every room), and one master limiter stage (a compressor, then a −1 dBFS ceiling). The listener follows the head (`setListenerPose`). There is no HRTF switch in this interface: at most 2 HRTF "hero" panners may be added, and only after a device A/B (T-129, W1) justifies them. *Cut (D-021, D-025):* `setReverb('small'|'medium'|'large'|'off')` (three reverb sizes) and `chordTone(degree: 0 | 2 | 4)`; the signatures above replace them. *Cut (v1.2 review):* the numeric argument of the draft `setReverb(decay: number | 'auto' | 'off')`: Settings has three states and nothing ever passed a number.
**As built (v1.2.4, T-121).** Before the first `setSignature` the engine plays C major pentatonic, the Wanderer tuning, with the default 0.9 s reverb. `preview` does nothing yet and is safe to call (T-147); `ui` is built (T-164 §6; `chordTone` in T-142b, `enterListen`/`exitListen` in T-148 and T-164, `ui('goodnight')` in T-148). The rules for the UI sounds (T-172, P-025): the first note at the audio clock's current time, never the next scheduler step; notes from the room's `chordDegrees`; a level of −10…+3 dB against a full-height plant of the same voice (`UI_LEVEL_DB_RE_PLANT`: dB of one note's gain, not loudness against the mix); at most 70 ms from the pinch to the sound, measured on the device; Bell, Pad, Pluck, Bass and Choir plants play their own voices (T-144); a Shimmer plant (Should S5) rings as a bell at its own octave and mix level until its voice is built. A step the scheduler finds more than 100 ms late is skipped (LLD §5.3). A note's sources and envelope are created per note; the channel strips and the note records are pooled, and the Pluck strings are cached (LLD §7.1).
**As built (T-143).** `setSignature`, `syncPlants` and `setReverb` render nothing in the call; the call makes the buffers the renders fill, empty. The engine's 25 ms tick does the rendering before it schedules: 2 Pluck strings a tick while any are waiting, otherwise 8 000 samples of a new impulse response (`PLUCK_STRINGS_PER_TICK`, `IR_SAMPLES_PER_TICK` in `audio/config.ts`, NFR-PERF-05). The slice that ends a channel also scales that whole channel to `IR_ENERGY` (T-172, P-022; it was to its peak, with the convolver normalising), one more pass over its samples (96 000 multiplies at 2.0 s). A tick that renders makes no buffer and puts no sample on the heap (NFR-PERF-08; measured in Node, pinned by a test each): a response slice grows the JS heap by 1 000 to 1 400 bytes, where it was 321 000 while the noise came from a generator called once per sample, and a string by 250 to 365 bytes, where a tick with two strings made two buffers and about 4 400 bytes of numbers. The noise generator (mulberry32) is therefore written out in the two render loops. `init()`, inside the Enter gesture, renders the first response whole, so the first notes are not dry, and one string to no buffer, so the string loop is compiled before a tick needs it (the first string of a process takes 4 to 5 ms, the next ones 0.3 ms). A re-tune of a full bed of plucks with a new 2.0 s decay, in Node on a laptop (2026-10-12): the call takes 0.1 ms and the costliest tick after it about 0.65 ms (median of 600 re-tunes in 12 runs), where the call took 12.3 ms before (worst 19.9 ms). The single worst of the 3 000 ticks of a run is not a clean figure on that machine, which was busy with other work (load average 5 to 11): 1.6 to 3.0 ms in seven runs, 6 to 51 ms in the other five. After the review fixes (four more runs) the call takes 0.12 to 0.17 ms, because it now makes the 20 string buffers, a response slice 0.28 ms where it was 0.45, and the costliest tick is a tick with two strings, about 0.6 ms. In a fresh process, as at a session start, the costliest tick of the first strings ever rendered was 3.1 to 3.6 ms (five processes) with the warm-up in `init()`; without it the first tick with strings took 5.2 to 6.6 ms (three processes). In desktop Chromium (`tests/e2e/09-audio.spec.ts`) the ticks of the spread take 0.1 to 0.9 ms. **One cost is left and it is the browser's, not the engine's:** putting a response into the `ConvolverNode` takes one tick about 2.8 ms per second of decay in desktop Chromium: 1.0 to 1.2 ms for 0.3 s, 2.0 to 2.3 for 0.6 s, 3.6 to 4.2 for 1.2 s, 4.1 to 4.8 for 1.6 s and 5.2 to 6.7 for 2.0 s. It cannot be sliced with one convolver, it was there before T-143, and a room with the default 0.9 s decay never pays it. Nothing here is measured on a headset (T-129), and no time is pinned by a test: the unit tests pin counts (strings and samples a tick, buffers made, heap bytes) and the browser test prints its tick times and asserts none of them, so every figure in milliseconds here is a report from one machine on one day. What plays meanwhile: every note at its pitch in the new key; a pluck whose string is not rendered yet plays the nearest rendered string re-pitched (LLD §7), so the plucks scheduled in the first 0.25 s after the call can have a slightly different tone. The step that was inside the look-ahead at the call is dropped and not played again. A note of the old key that was sounding fades over 20 ms; one that had already been stolen for a note of the dropped step keeps its fade and ends inside the look-ahead (0.12 s). The tail of the old key in the reverb rings out only when the decay stays the same. When the decay changes too, the old response stays in until the new one is whole (at most 0.85 s after the call); then the return is muted for 0.12 s for the swap, and that mute cuts what is left of the old tail. A newer decay drops a response that is still being rendered, and also one that is whole and waits for its swap: it never goes in, and the return opens again on the response in place. A decay equal to the one the convolver holds is neither rendered nor swapped (Settings: small, then auto again at once). **For the wiring (T-128).** The swap lands 0.25 to 1.0 s after the call and the caller cannot place it more exactly, so the tuning ripple should not start before it. A restored garden's first pluck notes after `init()` are stand-ins until their strings are rendered: 4 to 7 notes of a full bed of plucks at 60 to 120 BPM (3 when all its plants share a hue, none in a garden of one pluck a step), re-pitched by up to 9 semitones in the outer rings of the default key and 10 in the other two modes.
**As built (T-145, the spatializer).** The 24 pooled equal-power panners, their distance curve, the one shared reverb and its single send were in place from T-121 and T-143; T-145 changed the listener and added the click checks. `setListenerPose` sets the first pose and glides after it, as the signature comment says; before, it wrote nine values a frame, which stepped all 24 pans 72 times a second. The nine listener parameters and each panner's position and orientation are k-rate: Chromium pans every sample of every panner while automation runs on an a-rate one, which tripled the graph's cost while the head moved. A k-rate position changes only at a render-quantum start (`RENDER_QUANTUM` = 128 samples), so the pool places a note's panner at the quantum start at or before the note, judges a free channel there and ends a stolen note's fade there; an immediate sound that steals starts 20 to 23 ms late (LLD §7.1). A call is allocation-free (a heap test, under 1 byte a call over a million calls) and takes about 5 to 13 µs in desktop Chromium (a mean: the page's clock counts in 0.1 ms steps). No clicks at 24 voices (TC-AUD-04): a full bed that steals all the way, and 24 held pads, under a head posed once a frame, are rendered in desktop Chromium and the largest step in the samples is bounded (LLD §7.1 has how it is measured, the bounds and the readings when the code is broken on purpose); a unit test checks on the graph, over 13 bars of all five voices, that no panner moves while a note sounds through it. Cost, in ms of wall clock per second of audio of an offline render that is suspended every 13.3 ms for the pose and the ticks (the suspends are part of the figure; 24 pads with none render in about 74): 24 held pads 109 with the head still and 153 turning at best, where the a-rate glide took 390 to 450 turning and the stepped writes about 200; a busy, shared machine spread the figures 2 to 6 times from run to run. Not measured on a headset (NFR-PERF-06 is a device check, T-129). *Not built, and why:* the HRTF "hero" panners (no device A/B yet; two of them cost no measurable render time on desktop) and the `latencyHint` fallback (W1 has not run; it is one argument to the `AudioContext`, LLD §7.1). A `timeoutMs` that is not finite counts as expired. `flags.forceLevel` starts the chain at that level, and a forced level that cannot place still falls on to the next. Forward is the level direction square to the head's right vector, and every distance of FR-ROOM-01 and FR-ROOM-03 is measured level (horizontally) from the head. Pitch therefore does not move the bed, and a user looking straight down at the table still has a forward; head roll does move it (20° of roll at 45° of pitch shifts the spot by about 11 cm). A frame whose head pose is not finite, or whose head lies on its side, is skipped: the run waits for a usable one. The solver emits `room:placementLevel` (§2) once for each level it tries. Do not call `run()` from a `room:placementLevel` handler: the new run would be resolved with the old run's bed. `E_PLACEMENT_TIMEOUT` is logged at warn when a wait ran out and the chain ended at level 4 (§5). A plane qualifies at level 1 when it is level, labelled a table (`TABLE_LABELS`) and 0.5–1.1 m above the floor (`SURFACE_MIN_HEIGHT_M`..`SURFACE_MAX_HEIGHT_M`, the band level 2 uses; BUG-010, 2026-10-23: a 0.42 m coffee table had put the bed 1.18 m under the eyes), and at level 2 when it is level and in the band; one outside the band falls through to levels 3 and 4 as any unusable plane does.
**The anchor store as built (T-162).** `AnchorStore` is a class, like the three adapters, and `setFrame` is part of its contract. A frame can be used only inside its own callback and a promise continuation runs after it, so the store does all frame work inside `setFrame`: the `frame.createAnchor` that a `create()` left for the next frame, and the read of a restored anchor's pose. `supported`, `restore`, `create` and `clear` may therefore be called from anywhere, inside a frame or not, and a caller's continuation only keeps the result for its next `update` (§1.10 rule 4). `supported()` is false until a session's first `setFrame`: the choice between restoring and the chain is made in the first `update` of a session, not in the `xr:sessionStart` handler. A frame the store cannot use (its session cannot be read) is skipped and logged once at warn (`anchor frame failed`).
- **`restore`.** The device is asked with `session.restorePersistentAnchor(handle)`. It is not asked again while that request is out or while the store holds the handle's anchor in this session; it is asked again after a refusal, after a `clear()` or a `create()`, for another handle, and in a new session. The promise resolves with the pose of the first frame in which the anchor has a usable one (16 finite numbers, rigid). The pose is read once per call: the bed does not follow the anchor during the session, as a bed placed by the chain does not move either. A frame in which the anchor has no pose (not tracked) only makes the wait longer; the wait ends with `null` after `timeoutMs`. **A pause does not cost the saved place:** for as long as a restore waits, the store follows the session's `visibilitychange`; the time-out stands still while the session is hidden (no frame comes then, so no pose can) and starts anew, in full, when the session is seen again. Also `null`: unsupported; the device refuses the handle (unknown, another room, storage cleared); the read throws; the session ends or another begins; `clear()` or `create()` is called; a `create()` is on its way. A refusal, a time-out and a failed read are logged at warn as `E_ANCHOR_RESTORE`. Asked again for the same handle while it waits, `restore` returns the same promise and starts the time-out anew. A handle given to `restore` is the store's own from that call on, also when the call gives `null` at once (unsupported, before the first frame): a later `create()` or `clear()` deletes it. The anchor that a `create()` made is kept for the session, so `restore` of its handle reads the pose again without a call to the device (after a recentre, after a pause).
- **`create`** returns `Promise<string | null>`; `null` is "no anchor", as with `restore`, so no caller needs a `catch` (nothing catches a throw in a continuation: §1.10 rule 12). In order: the delete of the old handle is asked for and not waited for; `frame.createAnchor(pose, space)` in the next frame; `anchor.requestPersistentHandle()` when the anchor has arrived, a frame later. `null` when: unsupported; the pose is not rigid, or is a mirror image; a call is refused or missing, which includes a device that keeps no more anchors (the anchor just made is then deleted from the session); `ANCHOR_CALL_TIMEOUT_MS` (4000, `room/config.ts`) pass without a handle; the session ends or another begins; a later `create()` or a `clear()` replaces it. What the device delivers late, for a `create()` that was given up, is asked to be deleted again: an anchor from its session, a handle from the device. When that delete is refused (the session has ended), the handle stays until the sweep of the next `create()`. A failure is logged at warn (`anchor create failed`); a delete that fails is logged at info and stops nothing. That time-out is wall-clock time: a session hidden in the frames after a placement can cost that session its new anchor, and the next visit then places the bed by the chain.
- **The sweep.** With its handle in hand, `create()` asks the device to delete every other entry of `session.persistentAnchors`. The site keeps one anchor, and the Quest Browser allows a site eight. The sweep takes what would otherwise stay for good: a handle that was lost with the save, a delete the device refused or never answered, a handle that came after its session had ended, a handle that a later `restore()` replaced in the store, and the anchors of another page of the same origin (the test page `proto/spike/` makes one). A browser that has no `persistentAnchors` is not swept. A delete that is refused is logged at info and fails nothing.
- **`clear`** ends a `create()` and a `restore()` that are on their way and has the store's anchor deleted (`session.deletePersistentAnchor`). It resolves when the device has answered, at the latest after `ANCHOR_CALL_TIMEOUT_MS`, also when the device refuses. In a session without persistent anchors it touches nothing and keeps the handle for a session that has them. `create()` deletes the old anchor itself, so `clear()` before it is allowed and not needed. `clear()` does not sweep.
- **One anchor, and which.** The store's own anchor is the last handle it was given by `restore()` or made by `create()`; it remembers it from one session of a page to the next. `create()` has it deleted before it makes the new one, and the sweep deletes every other. The sweep needs IWSDK's `SceneUnderstandingSystem` to be off, which it is (`features.sceneUnderstanding: false` in `iwsdk.config.json`, D-040): when on, that system restores a persistent anchor of its own at session start, or makes one when it has none (`localStorage` key `iwsdk_scene_anchor_uuid`), and reads its space in every frame, which throws once the anchor is deleted (read in the IWSDK 1.0.1 source, not run). Nothing in `src/` uses that system; the room adapters read `frame.detectedPlanes` and `frame.detectedMeshes` themselves, from session features that do not depend on it.
- **Origins.** An anchor belongs to the origin that made it, as the save does. The two hosts (GitHub Pages and the mirror) are different origins: a garden and its place saved on one are not found on the other, and there the bed is placed by the chain.
- **Emulator and headset.** IWER 2.5.0 has `frame.createAnchor`, `anchor.requestPersistentHandle`, `session.restorePersistentAnchor`, `session.deletePersistentAnchor` and `session.persistentAnchors`; `tests/e2e/13-anchor-store.spec.ts` makes an anchor beside a stray, sees the stray swept, reloads the page and gets the same pose back. IWER keeps an anchor as a matrix in `localStorage`, restores every handle it knows in the next frame, has no limit, never loses tracking, and its delete leaves the stored matrix in place (the handle is back after a reload). The pause rule is unit-tested only: an emulated anchor always has a pose in the next frame, so there is no wait to pause. Whether a Quest finds the anchor again, how long that takes, the drift, the limit of eight and what a pose looks like before the room is recognised are device checks (TC-DEV-05, T-129).

**Placing the bed** (RoomSystem; once per session, and again on Re-place; LLD §5.5). This is how an anchor travels in both directions:
1. RoomSystem takes the saved pair `{ anchorHandle, anchorLevel }`, or its absence, from the state of the latest `garden:changed`: the first one of a page comes from `GardenSystem.load`, before any session (§1.10 rule 6). Nothing hands it over, and `room/` never reads the store.
2. In the session's first `update`, after `setFrame` (not in the `xr:sessionStart` handler: `supported()` is false until the store has seen a frame), with a pair: `restore(anchorHandle, ANCHOR_RESTORE_TIMEOUT_MS)`; its continuation only keeps the result. In a later `update`, a pose within reach (D-041: head to bed centre at most `BED_CENTRE_MAX_M` + 0.10 m, in front of the user) → `BedPlacement { pose, level: anchorLevel }`, then `room:placementLevel` and `room:bedPlaced { restored: true }`. The chain does not run.
3. Otherwise (no pair, unsupported, `null`, timeout, a restored bed out of reach): `PlacementSolver.run()`, then `room:bedPlaced { restored: false }`, on which garden drops a stale pair. After that, holding nothing up: `create(pose)` (it has the old anchor deleted itself and sweeps strays), and `room:anchored { handle, level }` in the `update` after it resolves with a handle; `null` emits nothing; garden stores the pair with `setAnchor` and the normal save persists it.
4. In both cases `RoomFeatureExtractor.extract(placement)` runs next and `room:features` follows. A bed restored at level 1 or 2 gets its room signature again; only a bed that was placed at level 3 or 4 is Wanderer, as it was on the day it was placed.

**As built (v1.2.3, T-124).** A `gesture:*` payload is the `GestureEvent` member of that name, `type` included, and it is an object the emitter reuses for the next event of that kind: a handler reads it at once and copies what it keeps. `gesture:palmUp` fires when an idle hand has held its palm up for `PALM_UP_HOLD_MS` (FR-HND-05), and again every `PALM_UP_HOLD_MS` while the pose holds and the hand holds nothing, each hold counted from the sample that fired, so a page back from a pause asks once (T-127). A pinch of that hand, an untracked sample or a palm turned away starts the hold over. hands does not look at the seed supply: garden decides whether a seed is delivered and ignores an ask it cannot serve (no visit yet, a seed already out); the repeats make up for it. `gesture:release.cell` is the hovered cell (T-116, below the table). `gesture:pull` and `gesture:drag` are built by T-146 (below the table). Not built yet, declared only: `gesture:palmsOut`, `gesture:wake`.

**As built (T-148).** `gesture:palmsOut` and `gesture:wake` are emitted by HandSystem after the machines. Palms out, only outside Listen: both palms (one in one-hand mode) open, each within `PALMS_OUT_MAX_ANGLE_DEG` 40° of the head's forward, held `PALMS_OUT_HOLD_MS` 1.5 s; a palm within `PALMS_OUT_MIN_DOWN_ANGLE_DEG` 30° of world down is not counted (D-050). Wake, only inside Listen: a palm within `WAKE_MAX_ANGLE_DEG` of the way to the head and within `WAKE_MAX_DISTANCE_M` 0.45 m of it (D-050), held `WAKE_HOLD_MS` 600 ms. GardenSystem starts Listen on palms out or a press of the Listen orb only after the session's visit (never while the room is being found), and ends it on wake, any pinch (which then does nothing else: no drag, remove, pull or press; a carried seed is still let go), a pause or session end; no seed is handed out during Listen.

`gesture:release` by `gesture`. `zone` is `bedZone` of the bed-local release point in every row; with no bed placed it is `'inner'`, the zone where a release commits nothing (the same answer garden gives for a point it cannot place, §1.1). `'outer'` on a dragged plant = remove (FR-HND-11). Garden reads `gesture` and never infers it from `zone` or `target`.

**Hover as built (T-116, FR-HND-16).** On every tracked sample the machine works out the hover first and only then looks at a pinch that starts or ends, so a pinch starts on the hovered target and a release commits to the hovered one. A hand that carries a seed hovers a cell: `target: null`, `cell` = `nearestFreeCell(stickyCell(point))`, asked again on every sample because the other hand may fill the cell meanwhile; `null` with no bed, off the bed or on a full bed. `gesture:release.cell` of a `carry` is that cell. A hand that drags a plant hovers a cell the same way, with that plant's own cell counted as free (its id is garden's `ignorePlantId`), and `gesture:release.cell` of a `drag` is that cell (T-146). A hand that holds a plant it does not drag (pinched inside the dead zone, or pulled) hovers that plant for as long as it holds it, whatever the distance and whatever else is nearer: `target` = the held plant, `cell: null`, so a pull never has a cell (T-146; as T-116 built it, such a hand was picked for like an empty one and lost its hover 4.5 cm from the plant). Every other hand (idle, pressing, pinching nothing) hovers a target: `target` = `pickTarget(point, candidates, kept)`, `cell: null`. A `press` keeps its target only if the hover is still on it at the release. `target:hover` is emitted when `target` (kind and id) or `cell` (ring and step) changes, never otherwise; its payload object is reused, and so is the `target` in it, which is the machine's own object: a listener copies the kind and the id it keeps (with the `eventLog` flag, §3, the log holds that one object for every logged hover, so it shows the latest values).

**One-hand pick as built (T-160, D-048, UX §9.1; emulator only).** While a hand is IDLE and `context.oneHand` is true, a hover that finds nothing at `pinchPos` picks again at that hand's `palmPos`, among the seed candidates only (`pickTarget(..., 'seed')`), with the same memory: a plant nearer the palm does not block the take (T-160 review). So the seed resting on that palm (within `HIT_RADIUS_M`, `HOVER_DEAD_BAND_M` more while it is the hover) is the hover, and a select of that same hand starts on it: `gesture:pinchStart` names it and the carry, the plant and every release are as with two hands. Any target within reach of the pinch point comes first. A pressed, pinched, held or carrying hand never picks at its palm. `pickTarget(pos, candidates, kept?, only?)`: `only` (T-160) restricts the pick to candidates of that kind. One-hand mode off: unchanged, the asking hand's pinch takes nothing off its own palm. Tests: `GestureMachine.test.ts` (one-hand), `tests/e2e/24-one-hand.spec.ts`.
**Shaping as built (T-146, FR-HND-08/10/11; emulator only, nothing of it has been on a headset).** A pinch on a plant starts as PINCHED and is measured from the `pos` of its `gesture:pinchStart`. Inside `DRAG_DEAD_ZONE_M` (travel under 2 cm, in any direction) nothing reacts, and a release there is `none`, as before. On the first tracked sample at 2 cm or more the larger part of the travel decides, for good: vertical at least as large as level → PULLING, else DRAGGING; a tie is a pull. "Vertical" is the travel along the bed's own up (the second column of `bedPose`), so a bed that is not level (a restored anchor can give one) is measured in its own frame; with no bed it is the world's up. The two parts are compared squared (`up² ≥ travel² − up²`). A decided pinch never changes: a pull that drifts over other cells or off the bed is still a pull and moves nothing, a drag that rises is still a drag. **Order in one tracked sample:** the travel and the decision, then the hover, then the release if the pinch has opened, else the preview. So the sample that decides already hovers and previews as what it decided. The travel is read only while the pinch is closed: the sample on which it opens is not measured, because opening the fingers moves the pinch point (T-146 review). A pinch still inside the dead zone then is released as `none`, wherever that sample is (also a hand that comes back from a loss open and far away); a pull commits the `dy` of its last preview; a drag commits the cell and zone of that sample's hover, which is the cell the hover showed. **Previews.** `gesture:pull { hand, target, dy }` once per tracked sample while PULLING and `gesture:drag { hand, target, pos, zone }` once per tracked sample while DRAGGING, from the sample that decided to the one before the release; none on an untracked sample. `target` is the machine's own object and the payloads are reused, like every `gesture:*`. They commit nothing. **Release.** `pull`: `dy` is the travel along the bed's up since the pinch began, as of the last closed sample (the `dy` of the last `gesture:pull`), always a number, never `null`; `cell` is `null`. `drag`: `zone` and the hovered `cell` as in the table, `dy: null`. **Loss and session end.** PULLING and DRAGGING freeze, come back and revert like every held state (below): after the grace `gesture:trackingLost { hand }` and no release, so the plant ends where and as tall as it was; `reset()` does the same at once. **A plant that is gone while it is held** (the other hand dragged it off, or New garden): the machine does not look; its previews and its release still name the id, and `GardenSystem` finds no such plant and changes nothing. **Cost.** The machine creates nothing per frame in these states, previews included (`GestureMachine.heap.test.ts`, 100 000 frames). Once per pull release it costs one boxed number, 16 bytes: `gesture:release.dy` holds a number or `null`, so V8 boxes the fraction written there. One thing to know when testing: an object of a preview's shape with a non-number in `dy` (a test's `{ type, hand, target, dy: expect.closeTo(…) }`) makes V8 box every fraction the machine then writes to its own payload, 16 bytes a frame; nothing in `src/` builds such an object.
**Tracking loss as built (T-116, FR-HND-15).** The first untracked sample after a tracked one emits `hands:lost { hand, held }`: `held` is the seed, the plant or the pressed target that hand holds, `null` for an idle hand and for a pinch on nothing; the payload object is reused, and `held` is the machine's own object, so a listener copies what it keeps. From that sample a hand that is not idle is frozen: nothing starts or ends, and its hover stays as it was. An idle hand's hover is cleared at once (`target:hover` with both `null`, only if it had one). The first tracked sample after it emits `hands:found { hand }` and the gesture goes on from there. The grace is counted from the first untracked sample: at the first sample of that hand, tracked or not, that comes `TRACKING_GRACE_MS` or more later, a hand that is not idle emits `gesture:trackingLost { hand }`, clears its hover and is idle, and no `gesture:release` follows; if that sample is a tracked one, `gesture:trackingLost` comes before `hands:found`. A pinch that is still closed when the hand comes back after a revert starts nothing: only a new closing does. `reset()` does the same revert at once and then forgets everything, the pinch edges too: a hand first seen pinching in the next session starts a pinch, as on a new machine. A first sighting of a hand is not a return: no `hands:found` without a `hands:lost` before it.
**HandSystem as built (T-116).** It builds its own `HandSampler` and does nothing outside an XR session (a frame with no XR frame or no reference space): the garden window (T-114) adds the way to give it another source. In a session, each frame, in this order: `sampler.setFrame(frame, referenceSpace)`; the context; then for each hand `sample`, `machine.update` and the `HandState` write. **The context.** One candidate per `Interactable` entity. Its `kind`, `id` and `worldPos` are read every frame, so an entity that is reused for another plant is that plant in the next frame. Its `radius` is read once, when the component is added, and raised to `HIT_RADIUS_M`: to change it, remove the component and add it again (read every frame it cost a boxed number per target). `bedPose` is the `matrixWorld.elements` of the `BedAnchor` entity that was added last of those there are; when that one goes, the one added before it is the bed again. It is `null` in a frame in which no entity carries a `BedAnchor`, and in one in which the chosen entity has no `object3D`. `nearestFreeCell` works on the state of the latest `garden:changed`, and every cell is free while there has been none; the id a machine gives it for a dragged plant goes to garden's `ignorePlantId` (T-146). **Time.** The sampler and the machines get IWSDK's frame time, the `time` of `update(delta, time)`, in whole milliseconds (`Math.round(time * 1000)`): the render loop's clock, which never goes back. Core's `clock.now()` (§1.0; wall time, which can step) is read once per hint, for the caption's `expiresAt`, which is on that clock. **Cost per frame.** 0 bytes, measured in `HandSystem.test.ts` with 80 targets at fractional positions and times of real size (a frame time of 12 345.678 s and on, a wall clock of 1.79e12). The same while one hand drags a plant over a bed of 80 targets with its hovered cell changing on every frame, a search of the bed behind every other one (T-146): 0 bytes and 0.016 ms a frame on a laptop, with a `gesture:drag` and a `target:hover` emitted in each. Two things keep it there: a candidate's position is a `Vector3`, and the time is a whole number. A fraction written into a plain `{ x, y, z }`, or handed to the sampler and the machines, was boxed: 16 bytes each, and 32 bytes a frame for the time. The price of the whole number is a filter time step that is a millisecond coarse (13 or 14 ms at 72 Hz): provisional until the device run. The number was measured on stand-in entities, not on the ECS, and leaves out the sampler's own joint reads (`getJointPose`, a known shortcut) and what IWSDK spends to call the system. On `xr:sessionEnd`: `sampler.detach()`, `reset()` on both machines, both hints taken back, both `HandState`s untracked. **The hint.** Since T-150 the hint is the icon `ui/Hints` draws (a palm in a dashed ring, 4 cm above the palm, clamped by the FoV guard); hands raises no caption.

Every frame `petals.update(frameMs)` after `plants.update`. The garden's handlers must run before this system's on the same event, as they do: `GardenSystem` subscribes in its constructor, before any system's `init()` (§1.10).
One luminance change = one swing of an element's brightness in one direction of at least `FLASH_MIN_DELTA`; a flash (up and back) is two changes. A swing counts from its last movement: one that moves on after a pause is timed at that moment, so no more than two further changes fit into the second after it (T-119; LLD §5.9). An element = one drawn instance (one plant, one cell marker, one beat-ring tick, one ripple quad, the halo, the tide wedge). The cap is half of what WCAG's three-flashes rule allows, so NFR-ACC-01 holds with margin. Enforcement and its consequences: LLD §5.9. `perf:sample.maxFlashPerS` (§2) reports the worst element.

**Rules a task may rely on.**
1. **The boot chunk.** `src/index.ts` and everything it imports without `import()` load neither `@iwsdk/core` nor `three`: the landing page is on screen before the SDK has arrived. That is `ui/Landing.ts`, `ui/strings.ts` and `core/` without `core/components.ts`. A file that joins that graph keeps the rule; a test follows the imports from `src/index.ts` and fails on either package.
2. **One way in.** `world.xr.offer` is `"none"` in `iwsdk.config.json`: a session starts from the page's Enter click only, in the emulator and on a headset. `engine.init()` and the session request are both made inside that click. A session therefore has sound or the `E_AUDIO_CONTEXT` caption: the caption is raised at `xr:sessionStart` when `init()` rejected or was never called (the dev plugin's native XR control can start a session with no click), and `AUDIO_START_GRACE_MS` (3000) later when `engine.clock.now()` has not moved since `xr:sessionStart` (0 on a first entry; on a later one the clock stands where the last session left it), because a context the browser will not start rejects nothing.
3. **A session is two bus events.** `src/app.ts` emits `xr:sessionStart`, `xr:sessionEnd` (only for a session whose start it emitted) and `xr:visibility { visible }`, where `visible` is `session.visibilityState !== 'hidden'`, emitted on a change, from the session's own `visibilitychange` event. `world.visibilityState` is not a substitute: IWSDK sets it inside the render tick, and a hidden session has none. A system starts and ends its session work on those events and reads XR objects only where it needs them: the session in an `xr:sessionStart` handler is `this.renderer.xr.getSession()` (`world.session` is set later); the frame is `this.xrFrame`, which is `null` outside XR; the reference space is `this.xrManager.getReferenceSpace()`; the head is `this.xrManager.isPresenting ? this.player.head.matrixWorld : this.camera.matrixWorld`. A system written that way runs unchanged in the garden window. **Pause and resume (T-152):** on `xr:visibility { visible: false }` the engine fades 0.2 s and suspends, the save flushes (T-128e); on `{ visible: true }` the wiring watches the audio clock for AUDIO_START_GRACE_MS as at the session's start: a clock that has not moved raises `soundResume` ("Pinch to resume sound") and the first `gesture:pinchStart` or `gesture:palmUp` (the dwell's select in gaze mode) calls `engine.resume()` once and takes the caption back; the session's end disarms it. The bar phase is continuous across a pause because a suspended context's clock stands still; the 2.5 s fade-in (T-173 part 1) covers the return; a long gap is one guarded brightness change for the halo and the ripple.
4. **The order inside a session.** `xr:sessionStart` → `room:placementLevel` (one or more) → `room:bedPlaced` → `room:features` → `room:signature` → `garden:changed` (the visit) → `garden:grown` (when plants grew) → `garden:seedArrived` (one per new seed). Everything from `room:bedPlaced` on is emitted in one frame, inside `RoomSystem.update`, with this frame's `XRFrame` readable; nothing is emitted from a promise continuation. That one frame may take up to 50 ms of script time (LLD §3.3 D). Plants sound, and the tide shows, from `room:signature` on and not before. `room:tuned` follows 4.0 s later once the ripple is built (T-142); the wiring does not wait for it. This is the order of emission, not of delivery: `GardenSystem` answers inside `room:bedPlaced` and inside `room:features`, so every other module receives `garden:changed` (the stale pair dropped) before `room:bedPlaced`, and `room:signature`, the visit's `garden:changed`, `garden:grown` and `garden:seedArrived` before the `room:features` of the same placement. A module that needs both the signature and the surfaces (the ripple) acts in its `room:features` handler or its next `update`, never on `room:signature` alone.
5. **The bed.** One entity for the life of the page, `RoomSystem.bed`. It carries `BedAnchor` exactly while a bed is placed: not before the first placement, not during Re-place, not after `xr:sessionEnd`, and not while the level-3 ghost shows. A query on `BedAnchor` is how a system learns "placed" and "no longer placed". Where the bed is drawn is `bed.object3D.matrixWorld`, which includes `bedHeightOffset`; `room:bedPlaced.placement.pose` is the surface's pose without it, and is what an anchor is made from.
6. **The garden's state** changes in `GardenSystem` only. Every change is one `garden:changed { state, diff }`, emitted after the state is replaced; a call that changes nothing emits nothing. The first one of a page comes from `load()`, before any session. A module that wants a change sends the gesture event the release table of §1.4 names, or calls one of the methods above. A handler of an event `GardenSystem` emits (`garden:*`, `room:signature`) never changes the garden from inside that handler: no `GardenSystem` method, no `gesture:*` or `room:*` emit; it does so from its next `update`. Otherwise handlers subscribed after it would see the inner change first and the outer one last. `GardenSystem` logs such a breach at error for `garden:changed`. The saver reads `garden.saved`, not the payload.
7. **Targets.** `Interactable.id` is the id the reducers take: a plant's id for `kind: 'plant'`, the seed's id for `'seed'`, and the removed plant's id for `'undo'`. A plant's `worldPos` is its cell centre on the bed (its foot), in world space, with `radius = HIT_RADIUS_M`. `BedRenderSystem` owns the plants' targets; whoever draws a seed, an orb, a petal or a control owns that target. `kind`, `id` and `radius` are passed to `addComponent` and never set afterwards: hands reads them once, when the component is added (§1.4); only `worldPos` is written later.
8. **Seeds.** `garden:seedArrived` = a seed joined the supply. `garden:seedOut` = the next seed of the supply rests on a hand; it is still in `state.seeds`. It is drawn at that hand's `HandState.palmPos` until a hand's `gesture:pinchStart` names it as its target (another hand's, or in one-hand mode its own: §1.4, D-048), and from then at the carrying hand's `HandState.pinchPos`. It stops being out in exactly two ways: `garden:changed` naming its id in `diff.added` (planted), or `garden:seedBack`, whose `reason` covers every other end, the session's end and `newGarden()` included. No seed is handed out before the session's visit.
9. **Saving.** Every `garden:changed` and every `settings:changed` is handed to the saver, with the live settings in the state, and written within `SAVE_DEBOUNCE_MS`; the saver is flushed on `xr:visibility { visible: false }`, on `xr:sessionEnd` and when the document is hidden. A module never calls the store or the saver.
10. **Brightness.** There is one `FlashGuard`. An element belongs to the object that claimed it, and only that object calls `request` for it, once per frame. A second effect on a plant (hover glow, bloom, Listen foreground) is handed to `PlantRenderer` and combined there.
11. **The tide's phase.** A renderer that follows the tide takes `engine.clock.barPhase()` only when the bed is placed, the session has its signature and `engine.clock.now() > 0`, and `NaN` otherwise. Before `init()` the engine reports phase 0, which is a valid phase, and during Re-place there is no bed to sweep.
12. **A throw does not stop the frames.** The helper catches a throw from a system's `update`, logs it and pauses that system for 1 s (LLD §8). It covers every system of the world: the ones registered through it, and IWSDK's own, which it wraps after the last registration. It does not reach three other places, and code there catches its own throw: a query's `qualify` or `disqualify` callback (it runs inside the caller's `addComponent`), a callback inside the render (`scene.onAfterRender`), and a promise continuation, which does no work in the wiring for that reason. A bus handler is covered by the bus (§2). `register` returns the instance, and throws at start-up for a priority lower than the previous call's and for a `configData` key the system's schema lacks.
13. **One space.** `world.player` is never moved (`locomotion: false`), so a pose in the XR reference space is a world pose.
14. **For browser tests.** With `Flags.dev` on, `window.__roomsong` is `{ world, engine, garden }` (T-128a, T-128d). Nothing in `src/` reads it. Events are read from the bus, which a test already reaches through the dev server's `/src/core/index.ts`.
15. **Nothing compiles mid-session (T-165).** On `xr:sessionStart` `src/app.ts` calls `renderer.compile(scene, camera)` once, in the first frame with a pose (at once in the garden window), so every program the app can draw, hidden meshes included, links before the first placement; it unsubscribes on `xr:sessionEnd` too. So a renderer makes every mesh and material in `init` and never changes a material's map, transparency or side later; it needs no warm-up draw of its own. A mesh whose instance count is 0 is hidden, and shown again with its next instance. The app adds no `AudioListener` (IWSDK's is removed from `player.head`: the audio has its own context, §1.2), turns IWSDK's hand rays off (`multiPointers[hand].toggleSubPointer('ray', false)`), and sets no `scene.environment` (no IBL: no material in `src/` is lit).

## 2. Event bus (`core/events.ts`)
Typed pub/sub, synchronous, no async handlers in hot paths.
`core/events.ts` owns the bus and the `EventMap` interface (§1.0), which holds only the events declared in `core/`: `settings:changed`, which core emits, and the three `xr:*` events, which `src/index.ts` emits (it owns the session; core cannot see it). Every other module adds the events it emits by declaration merging in its own `events.ts` (`declare module '../core/index.js' { interface EventMap { … } }`), so `core/` imports no payload type and a payload type lives with its emitter. The table is the merged map.
An `events.ts` must be a module, or the `declare module` block does not compile: it has an import (usually the `import type` of a payload type) or `export {}`. An empty payload, `{}` in the table, is typed `Record<string, never>` (lint bans the `{}` type) and emitted with `{}`. A copyable example is in the JSDoc of `EventMap` in `core/events.ts`.
During an emit (v1.2.1): handlers run in subscription order; a handler removed before its turn is not called; a handler added is first called by the next emit; a handler that throws is logged and the rest still run; emitting from inside a handler is allowed. With the `eventLog` flag (§3) every emit is logged at debug level.
A consumer never imports the emitter to name a payload: it writes `EventMap['gesture:release']`, with `EventMap` imported from `core/`. The merged map is a whole-program type, so this needs no upward import, but it typechecks only once the emitter's `events.ts` is in the program. `garden/GardenSystem.ts` consumes `gesture:*`, `hands:*` and `room:*` from the level above it. Two rules keep that from blocking anyone: (1) a module's `events.ts` holds declarations only, can be written straight from this table, and is the first file of the module to land, before any implementation; (2) garden's pure files never mention `EventMap`, so they build and test with `core/` alone.

**Settings and saving (v1.2.1, v1.2.5).** The `settings` store of `core/` is the live value, and it saves nothing. `PersistenceSystem` (§1.5) listens to no event: `src/index.ts` drives it. ## 3. URL flags (`core/flags.ts`) — dev/test only, ignored in prod builds unless `?dev=1`
`perfHud` · `fovGuide` · `eventLog` · `timeLapse` (starts the time-lapse demo at load, T-174) · `noAnchors` · `noPlanes` · `noMeshes` · `forceLevel=1..4` · `fakeDay=+N` · `seed=<int>` (deterministic variations) · `autoplant=N` (plants N seeds of its own, the same on every run, for perf tests: LLD §3.2) · `skipOnboarding` · `forceSignature=wanderer` (skip room features; use `WANDERER`) · `pinchTest` · `capSpike` (*Cut (T-104, T-105):* still parsed, read by nothing; the test pages are opened by address, `/proto/pinch/` (TC-DEV-00) and `/proto/spike/` (TC-DEV-0A)) · `window` (forces the garden window even where `immersive-ar` is supported, e.g. under IWER; FR-SYS-07, TC-E2E-14).
**Syntax and bounds (v1.2.1).** One query parameter, `flags`, holds a comma-separated list, and a second one, `dev=1`, is the gate in a production build: `?dev=1&flags=perfHud,forceLevel=3,fakeDay=+1`. A production build without `dev=1` gets the defaults whatever else the URL says (Vite compiles `import.meta.env.DEV` to `false`); a dev build needs no `dev=1`. A repeated `flags` parameter adds to the list. A boolean flag is on when it is listed bare or as `name=1`, and off as `name=0`. A number is a whole number in plain digits with an optional sign: `forceLevel` 1..4, `fakeDay` −3650..+3650 days, `seed` 0..4294967295, `autoplant` 0..80. `forceSignature` takes `wanderer` only. An unknown name, a malformed value or a value out of bounds is ignored: the flag keeps its earlier value or its default, and parsing never throws. Defaults: every boolean false, `forceLevel` null, `fakeDay` 0, `seed` null, `autoplant` 0, `forceSignature` null. `Flags.dev` reports the gate.
**Reading flags (v1.2.1).** `flags` is frozen and built once per page load. A system or class outside `core/` takes `Flags` as an argument that defaults to the singleton and reads it when it runs, never at import time; a test passes `{ ...flags, noPlanes: true }`. Never use `vi.resetModules()` in a test that imports `core/`: the ECS component registry is global, and a second declaration of `BedAnchor` throws.

## 4. Storage schema (IndexedDB db `roomsong`, store `garden`, key `state`)
`GardenStateV1` as in §1.1 (`bedInner`/`bedOuter` are stored as constants for forward compatibility; `bedRadius` never shipped). The room signature is **not** stored; it is recomputed each session (FR-ROOM-13). Backup at key `state.backup.<timestamp>`; keep the latest 2.
`settings` is the `Settings` type of §1.0; `settings.dwellMs` joins version 1 (nothing has shipped): the validator fills a missing `dwellMs` with 900; `settings.mono` joins it the same way (T-173): a missing `mono` loads as false. `anchorHandle` and `anchorLevel` stay optional and travel together: the anchor is Must, its absence is the re-placement fallback (FR-ROOM-07). `anchorLevel` joins version 1 too; the validator drops a handle that has no valid level, and the bed is then re-placed.
Migration policy: `migrations.ts` has `migrate(v: unknown): GardenState | null`; unknown versions → null (new garden, backup kept).

*As built (T-128e):* a storage whose state could not be read or backed up is never written again by that store in the session (the new garden goes to localStorage, and the next load's two-garden rule, D-033, keeps the older one); a newer-version save is kept in its backup; the trim of old backups never removes the one just written; a newer tab posts "opened" on a BroadcastChannel and older tabs stop saving.
**Backup (v1.2.5).** A state that is corrupt or of an unknown version is moved, not copied: it is written to `state.backup.<timestamp>` in the storage it was read from and the `state` key is deleted, so a second load makes no second backup. `<timestamp>` is ms on core's clock, all digits. Each storage keeps its own latest 2 backups.
**Fallback (v1.2.5; FR-PER-01, ADR-003).** localStorage holds the same keys under `roomsong.garden.` (`roomsong.garden.state`, `roomsong.garden.state.backup.<timestamp>`), each value as JSON; IndexedDB holds the object itself. A write goes to IndexedDB, and to localStorage only when IndexedDB refuses it or did not open within `IDB_OPEN_TIMEOUT_MS`; a write IndexedDB takes removes the localStorage copy. A localStorage copy is therefore the newer one, and `load()` reads it first. When both storages hold a valid state: with a different `createdAt` they are two gardens (a second one was started in a session in which IndexedDB did not open), and `load()` returns the older one, by `createdAt`, and moves the newer one to a backup key in its own storage (D-033), so that the grown garden stays in sight and no garden is ever overwritten or removed without a backup; with the same `createdAt` the copy with the later `lastVisitAt` is returned, the localStorage one on a tie.
**Validator (v1.2.5).** `load()` and `save()` both run it; it never throws. A value the app could not have written is refused whole: a `version` other than 1; a `bedInner` or `bedOuter` other than 0.12 and 0.30; a missing field or a wrong type; a number that is not finite; a `bedHeightOffset` beyond ±0.10; a plant `height`, or a `hue`, outside 0..1; a `cell` that is not a cell of the bed (ring 0..4, step 0..15, whole numbers); two plants in one cell; an id that is empty, longer than 64 characters, or used twice among the plants and seeds; a voice that is not a `VoiceType`; a `lastSeedDate` that is not `YYYY-MM-DD` with a month 01..12 and a day 01..31; `visits` that is not a whole number ≥ 0; more than 80 plants; more than 5 seeds (FR-MUS-08); a `codex.discovered` that repeats a voice. It repairs two things only: the settings (`validateSettings`, §1.0) and the anchor pair (kept when the handle is a string of 1..64 characters and the level is 1..4, else both are dropped). Keys that are not part of the schema are dropped at every level. The result is a new object, and its cells are garden's shared frozen ones (§1.1).
